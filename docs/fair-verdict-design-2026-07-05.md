# FAIRNESS FIX — ARCHITECTURE: "Provisional seal, one-shot revision, finality at window close"

All backend paths under `<repo>/backend/src/`, client paths under `<repo>/src/` and `modules/`.

## 0. The one-sentence design

Keep the 90s seal as a **provisional** verdict for display; accept the sealed-DNF runner's late finish for a bounded **10-minute revision window** (annul the seal, let measured-elapsed truth re-resolve, flip at most once); move **LP, result notifications, and saved-run backfill to window close** (finalization), so nothing irreversible ever happens off a provisional verdict; and on the client, make the finish upload survive iOS screen-off via the already-shipped native uploader (build 43) so the window is almost never needed. Note the codebase already embodies the fairness rule in one place: the no-session save resolver ranks by measured elapsed, faster wins (`matchResultBuilders.mjs:386-390`). The sealed live-session path is the single exception where receipt timing overrides measured truth — this design removes that exception.

## 1. Lever verdicts

**① Widen MATCH_DUEL_FINISH_FALLBACK_MS — REJECT (keep 90s).** iOS screen-off lag is unbounded (pocketed phone, minutes to tens of minutes); any finite widening still violates the invariant, and every extra second delays the on-time finisher's first feedback and the genuinely-dead-opponent resolution. 90s + provisional display + revision window strictly dominates any widened sticky seal. (Do decouple the constant from `MATCH_PARTICIPANT_RUNNING_STALE_MS` only if you ever tune one independently; no change now.)

**② Revisable seal — ACCEPT (core fix).** Bounded window `MATCH_SEAL_REVISION_WINDOW_MS = 10 * 60 * 1000` measured from `duelFallbackResolution.resolvedAt` (covers the observed 2–10 min screen-on lag; ≪ 4h session TTL). Mechanism = **annul, not edit**: a valid late finish inside the window deletes the seal and records a revision marker; the natural `bothFinished` verdict path (`matchSessionVerdicts.mjs:65,87-104`) then resolves by measured elapsed, including dead-heat. Flip count ≤ 1 is structural: only the one sealed-DNF runner can revise, finish freeze is first-write-wins (`matchActionHandlers.mjs:395-402`), and after both finishes are frozen nothing can change. Accept the late finish even when SLOWER (winner unchanged): the loser gets a real 패배 with their real time instead of DNF, and the every-done LP gate can finally pass. Plausibility guard on the client-reported elapsed: integer > 0 and ≤ wall-clock since `startedAt` + 120s skew slack (you cannot measure more running time than has physically elapsed); this is no weaker than the trust the in-window path already extends.

**③ Delay finality with provisional display — ACCEPT, merged into ②.** The seal itself stays at 90s for display; **LP + `match_result`/`rank_change` notifications + `backFillFinisherSavedRuns` move to finalization** (first persisting touch at/after `resolvedAt + 10min`). This is mandatory, not optional: if backfill writes `lose` into the iPhone's saved run at 90s, its own never-downgrade guard (`matchResultBuilders.mjs:778-786`) would permanently block the revision from correcting the record — the exact stuck shape observed. Deferral costs the winner's card ~8.5 extra minutes of 집계 중 (overlaid client-side with a 가확정 badge, Stage 3), and *grants* the winner LP they today never receive at all (the sealed path never passes the every-done gate — `matchActionHandlers.mjs:51` — so sealed wins currently strand LP forever). New explicit behavior: at finalization the DNF side takes the loser LP delta (`resolveDuelMatchLpDeltas`, `rankSystem.mjs:87-116`); the revision window is the fairness protection for that.

**④ Aggressive client finish flush — ACCEPT (probability fix, OTA-able on build 43/versionCode 34).** All five of Reader B's wins; details in §3. This makes >90% of finishes land inside 90s so no flip is ever shown; the server revision is the correctness net for the rest and for pre-build-40 iOS binaries with no native module.

**⑤ Surface consistency — ACCEPT, targeted.** Root cause of the stuck card is twofold: the two heal channels (`useRunDetail.ts` focus refetch + one-shot 95s `/status` reconcile with an empty catch at :112-114) both require a live session, while `/result` deliberately does not; and `/status` answers "no session" with an idle-shaped response instead of any terminal signal (`matchResponseBuilders.mjs` fall-through). Fix on the client with a `/result` fallback + terminal handling (§3), not by changing `/status`'s shape (old-client risk). Server-side, finalization-before-prune ordering (sweep runs first inside `pruneMatchSessions`, `matchSessionLifecycle.mjs:43`) guarantees both saved runs are back-filled before the session can vanish, killing the "pruned while pending" class at the source. One extra server rule: `resolveSavedDuelMatchResult`/`resolveSavedGroupMatchResult` must return PENDING while the verdict is provisional, so a provisional outcome is never persisted into a blob the backfill can no longer correct.

## 2. Server half — exact changes (one droplet deploy)

1. **`lib/matchConstants.mjs`** — add `export const MATCH_SEAL_REVISION_WINDOW_MS = 10 * 60 * 1000;`

2. **`lib/runningMatchSession/matchSessionFallbackSeals.mjs`**
   - Add `isSealWithinRevisionWindow(session, now)` — duel: `duelFallbackResolution && now - Date.parse(resolvedAt) < MATCH_SEAL_REVISION_WINDOW_MS && !session.sealFinalizedAt`; group twin reads `groupFallbackResolution`.
   - Add `annulSealForLateFinish(session, userId, now)` — duel: null out `session.duelFallbackResolution`, write `session.duelFallbackRevision = { revisedAt: now.toISOString(), lateFinishUserId: userId, previousWinnerUserId, sealResolvedAt }`. Group: same annul of `groupFallbackResolution` + marker; the sticky sealer re-seals on the next touch from raw state with the new finisher included at their measured-elapsed position (`:181-193` sort), so DNF-below-finishers order is recomputed, never hand-edited. Anti-thrash holds: re-seal is deterministic from participant state; only a new accepted finish changes it.
   - `sweepStuckMatchSessionFallbacks` (:23-59) gains a **finalization phase** per sealed session: if `now - resolvedAt >= MATCH_SEAL_REVISION_WINDOW_MS` and `!session.sealFinalizedAt`, set `sealFinalizedAt`, then run backfill + LP/notification (injected, see 4). **Gate the existing per-sweep backfill call (:53) on `session.sealFinalizedAt || everyParticipantDone`** instead of always — this is the never-persist-provisional rule, and the every-done arm closes the forfeit-during-window hole (leave → everyone done → prune would otherwise drop the session before finalization backfills). Persistence is inherited: the sweep already runs under `mutateStore` on `/result` (`routes/runningMatch/runningMatchProgressRoutes.mjs:59-63`), on every `/progress` and `/status` (:92, :130), and inside every prune from session finders; the single-JSON atomic write (`store.mjs:468-490`) commits LP + flags + blobs together, so `lpApplied` can never persist without its LP effect or vice versa.

3. **`lib/matchActionHandlers.mjs`** `updateRunningMatchProgress`
   - Between the seal calls (:354-361) and the `sealedAsDnf` downgrade (:362-372): if the pusher is sealed-DNF, `requestedFinished`, elapsed passes the plausibility guard, and `isSealWithinRevisionWindow` → `annulSealForLateFinish(...)` and proceed as a NORMAL finish (freeze at :383-411; verdict re-resolves from both measured finishes; `applyMatchLpIfComplete` at :421 fires because both are now done). Otherwise the existing downgrade stands byte-for-byte (beyond-window behavior unchanged, incl. `finishedAt = null` at :413-415).
   - Extract the LP+notification core of `applyMatchLpIfComplete` (:58-126) into `applyMatchLpFromStandings(store, session, standings, participants)` guarded by the same `lpApplied`/`resultNotificationApplied` one-way booleans; keep the every-done wrapper for the normal path and call the core from the sweep's finalization phase (where the DNF side is 'disconnected', so the every-done gate can't be reused). Winner is standings rank 1 — under a finalized seal that is the sole finisher; after a revision it is measured-elapsed truth. Register the finalizer alongside the backfill via the existing injection pattern (`registerFinisherSavedRunBackfill`, `matchResultBuilders.mjs:815`) or a sibling setter to avoid the import cycle.

4. **`lib/runningMatchSession/matchSessionVerdicts.mjs`**
   - Sealed duel branch (:72-84): add `provisional: !session.sealFinalizedAt` (true only inside the window). Non-seal resolved branch: add `revised: session.duelFallbackRevision?.previousWinnerUserId && session.duelFallbackRevision.previousWinnerUserId !== winnerUserId ? true : undefined` + `revisedAt` — set only when the winner actually changed. Group sealed branch (:181-209): same `provisional` flag. Additive fields; old clients ignore them.

5. **`lib/matchResultBuilders.mjs`**
   - `resolveSavedDuelMatchResult` (:94) and `resolveSavedGroupMatchResult`: when the verdict is `provisional`, return `toPendingDuelMatchResult(...)` / group twin — provisional outcomes are display-only, never persisted.
   - `buildResultFromSession` (:474-530): pass through top-level `provisional` / `revised` from the verdict so `MatchResultScreen` can badge them. No change to `buildResultFromSavedRuns` (post-prune runs are final by construction now).
   - Known follow-up, explicitly out of scope: the +20P match bonus is only granted at save-time off `resultTone`; a back-filled win never receives it (pre-existing for every sealed heal). Needs an idempotent points-reconcile keyed on matchId — separate change, do not bolt on here.

Store-cost audit: two small per-session fields (`duelFallbackRevision`, `sealFinalizedAt`) on live sessions only (≤4h lifetime), one `Date.parse` per sealed session per sweep, zero new polling, zero per-run growth — compatible with the #209 saturation constraint.

## 4. Test list (backend `node --test`, new `backend/src/lib/matchSealRevision.test.mjs` + extensions)

Contract timeline tests (fixture: duel, Galaxy finish receipt t0, seal t0+90s, window t0+90s+10m):
1. Regression pin: late finish at t0+60s → no seal, standings by measured elapsed, faster wins, LP once (the §5 counterfactual).
2. At seal: verdict `resolved && provisional`, winner=finisher; assert NO LP delta on either user, NO notifications, saved pending blobs untouched (deferred backfill), `resolveSavedDuelMatchResult` returns pending.
3. Revision, faster (1606 vs 1622) at seal+5m: seal annulled, both finishes frozen, winner=late runner, `revised:true`, LP applied exactly once to both sides, one `match_result` + one `rank_change` per user, backfill heals both blobs to truth on next sweep.
4. Revision, slower: winner unchanged, no `revised` flag, late runner recorded as real finisher (time visible), LP once.
5. Beyond window (seal+11m): push downgraded exactly as today ('running', `finishedAt` nulled), verdict stays sealed-final, blobs already back-filled 'lose', LP already applied at finalization; repeated pushes never change anything.
6. Finalization idempotency: hammer sweep/`/result`/`/status`/progress across the timeline — `sealFinalizedAt` set once, LP applied once (assert absolute rankState values), notifications once, `winnerUserId` changes at most once over the entire observed sequence.
7. Plausibility guard: elapsed 0 / non-integer / > wall-clock+slack → no annul, downgrade preserved.
8. Forfeit during window: DNF side leaves → immediate LP via every-done gate, backfill runs before prune drops the session, no double-apply at the (never-reached) finalization.
9. Group parity: late finisher within window un-DNFs, re-seal ranks them by measured elapsed among finishers, other rows' relative order preserved; beyond window blocked.
10. Restart durability: serialize/reload store mid-window → window math (absolute timestamps) and all guards behave identically.
11. Dead-heat revision (equal elapsed) → draw verdict; pin current LP behavior for draw (pre-existing semantics, do not change here).

Client (jest): native routing of pending finish (mock module), cadence carries finished body until ACK/terminal/10m cap, flush retries finish despite idle snapshot, `useRunDetail` /result fallback + 410 terminal + no re-arm after terminal, pending-finish cleared on final sealed-DNF status.
