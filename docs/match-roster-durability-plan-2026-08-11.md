## 1. 저장소 구조 조사 결과 (설계를 좌우한 사실들)

1. **스토어 전체가 드라이버 무관하게 단일 JSON 블롭이다.** postgres 드라이버도
   `app_store` 테이블의 `id=1` 행 하나에 통째로 jsonb로 넣는다(`postgresStoreAdapter.mjs:28`).
   → **새 최상위 컬렉션 하나 추가하면 json·postgres 양쪽이 자동으로 같이 내구화된다. DDL·마이그레이션 불필요.**
2. **`mutateStore`의 mutator는 반드시 동기 함수다.** 양쪽 어댑터가 async mutator를 명시적으로
   `throw`한다(`store.mjs:481`, `postgresStoreAdapter.mjs:312`). → **resolver 안에서 사이드 테이블을
   `await` 조회하는 설계는 구조적으로 불가능**하다(§2 옵션 B 기각 근거).
3. **세션 생성 길목은 `createMatchSession` 하나**다(호출처 5곳: 매칭 듀얼/그룹, 파티룸 2곳, 테스트).
   참가자 추가는 `addParticipantToMatchSession` 한 곳(그룹 지각 합류, 출발 전에만 가능).
4. **정당한 늦은 저장의 상한은 7일이다.** 클라 저장 대기열
   `src/features/runs/save/pendingRunSaveQueue.ts:23` → `PENDING_SAVE_MAX_AGE_MS = 7일`.
   → 로스터 보존기간은 **반드시 7일보다 길어야** "저장 대기열 드레인의 정당한 늦은 저장 해소" 계약이 산다.
5. **기존 내구 기록 중 로스터로 쓸 수 있는 것은 없다.** `notifications`의 `match_result`가 matchId를
   담지만 (a) 유저당 **50개 상한**으로 밀려나고 (b) **finalization에서만** 기록된다
   (정상 완주 대결은 봉인을 안 타는 경우가 있다). → 로스터로 못 쓴다.
6. `vanishedMatchTombstones`는 **프로세스 메모리**라(재시작 시 소멸) 내구 로스터가 못 된다.

## 2. 저장 위치 선택지

| | 방식 | 판정 |
|---|---|---|
| **A** | **스토어 블롭에 `store.matchRosters` 배열 추가** — 생성 시 기록, prune 생존, 나이 기반 GC | **추천** |
| B | postgres 사이드 테이블 `match_rosters` (`run_routes` 방식) | **기각(구조적 불가)** |
| C | 로스터 없이 no-session 분기를 항상 PENDING으로 | 조건부 대안 (§4) |
| E | 세션을 지우지 말고 **뼈대 세션**으로 남기기 | **기각(파급 과다)** |

- **B 기각 이유(선호가 아니라 구조):** 사이드 테이블 읽기는 async인데 resolver는 동기 mutator 안에서 돈다(§1-2).
  우회하려면 저장 경로 전체에 로스터를 미리 읽어 넘겨야 해서 판정 경로를 훨씬 크게 건드린다.
  게다가 json 드라이버(테스트·개발·스모크)용 두 번째 경로가 생겨 **테스트가 검증하는 코드와
  프로덕션 코드가 갈라진다**. 이 구역에서 그건 받아들일 수 없다.
- **E 기각 이유:** `store.matchSessions`를 순회하는 코드가 전부(hydrate·standings·큐 매칭·라이브 상태·룸 동기화)
  뼈대 세션을 보게 된다. `session.mode === 'duel'` 통과 후 `buildOfficialSessionStandings`가 빈 뼈대에서 도는 등
  파급이 너무 넓다. 로스터는 **세션과 분리된 별도 컬렉션**이어야 한다.
- **A의 유일한 실비용:** 블롭 증가 = #209(블롭 비대 → FOR UPDATE 락 연장 → 쓰기 컨보이)의 민감 축.
  그래서 §3에 보존기간·상한·GC를 못 박았다. 항목 1건 ≈ 110바이트, 14일치 현실 규모 ≈ 300KB 이하.

## 3. 추천안 상세 (옵션 A)

### 3-1. 새 모듈 `backend/src/lib/matchRosters.mjs` (리프 모듈, 순환 없음)

항목 모양 — **작게 유지가 핵심**:

```js
{ id: 'duel-match-ab12', mode: 'duel', participantIds: ['u1','u2'], createdAt: '2026-08-11T…' }
```

공개 함수: `ensureMatchRosters(store)`, `recordMatchRoster(store, session, now)`,
`amendMatchRoster(store, sessionId, userId)`, `findMatchRoster(store, matchId)`,
`pruneMatchRosters(store, now)`, `isMatchRosterEpochMature(store, now)`.

`ensureMatchRosters`는 `ensureMatchSessions`와 **같은 지연 초기화 패턴**을 쓴다 →
store 마이그레이션 목록에 손댈 필요 없음. (postgres 어댑터는 json 마이그레이션을 안 돌리므로
이 패턴이어야 두 드라이버가 동일하게 동작한다.)

### 3-2. 기록 시점

- `createMatchSession` 끝에서 `recordMatchRoster` — **5개 호출처 전부 한 번에 커버**.
- `addParticipantToMatchSession`에서 `amendMatchRoster` — 그룹 지각 합류(출발 전).
- ⚠️ 구현 메모: `createMatchSession`은 현재 `new Date()`를 내부에서 직접 부른다(`:146`).
  결정적 테스트를 위해 **`now` 주입 경로를 같이 뚫어야 한다**.

### 3-3. 보존기간·GC·상한

| 상수 | 값 | 근거 |
|---|---|---|
| `MATCH_ROSTER_RETENTION_MS` | **14일** | 클라 저장 대기열 상한 7일의 2배(시계 오차·오프라인 기기 여유) |
| `MATCH_ROSTER_LEGACY_GRACE_MS` | **7일** | 클라 `PENDING_SAVE_MAX_AGE_MS`와 **동일** — 정당한 늦은 저장의 실제 상한 |
| `MATCH_ROSTER_MAX_ENTRIES` | **5,000** | ≈550KB 상한. 넘치면 오래된 것부터 축출 + 로그 |

- **GC 위치:** `pruneMatchSessions` 안(모든 쓰기 요청에서 돈다). 항목이 **생성 시각 순으로 append**되므로
  앞에서부터 만료분만 잘라내는 **prefix drop** → 매 요청 O(만료건수), 사실상 O(1).
- **상한 초과 시의 안전 성질:** 축출된 매치는 "로스터 없음"이 되고, epoch 성숙 후에는 **PENDING(안전)** 으로
  떨어진다. **절대로 무방비 legacy로 떨어지지 않는다.** 이게 이 설계의 핵심 안전 성질이다.

### 3-4. no-session 분기의 소비 방식

공통 길목 `collectSavedMatchRuns(store, matchId)`에 로스터 필터를 넣는다. 호출처 3곳
(듀얼 resolver `:371`, 그룹 resolver `:269`, **GET /result `:766`**)이 한 번에 막힌다 —
결과 화면에 위조 참가자 행이 뜨던 것도 같이 닫힌다.

**듀얼** (`resolveDuelMatchResultFromSavedRuns`):
1. 기권 블롭 검사는 **지금 위치 그대로 맨 앞**(계약 보존).
2. 로스터 있음 → ① `currentUser`가 로스터에 없으면 **PENDING**(§5 문 A와 동일 처리)
   ② 후보 상대 = 로스터 멤버 중 나 아닌 사람의 저장 기록 ③ 없으면 PENDING(기존과 동일).
3. 로스터 없음 → §3-5 표.

**그룹** (`resolveGroupMatchResultFromSavedRuns`):
1. 기권 검사 그대로.
2. 로스터 있음 → `participantCount`를 **클라의 `matchResult.participantCount`가 아니라 로스터 크기**에서
   가져온다(패딩 벡터 제거). 로스터 멤버 전원이 저장했을 때만 봉인, 아니면 PENDING.
   - ⚠️ **행동 변화 1건:** 클라가 `participantCount`를 실제보다 **작게** 보고했을 때 지금은 봉인되지만
     앞으로는 PENDING이 된다. 더 엄격한 쪽이고 옳지만, 계약 변화로 명시해 둔다.

### 3-5. 로스터 없는 옛 매치 / matchId 없는 기록

`store.matchRosterEpochAt`(최초 1회 기록)로 **"로스터 없음"의 의미를 시간으로 구분**한다.

| 로스터 | epoch 성숙(≥7일)? | 동작 |
|---|---|---|
| 있음 | — | 로스터 게이트 적용 (안전) |
| 없음 | 아님 | **기존 동작 그대로**(legacy) — 배포 전 매치의 늦은 저장을 지킨다 |
| 없음 | 맞음 | **PENDING** — 정당한 늦은 저장은 최대 7일이므로, 그보다 오래됐으면 위조이거나 고대 기록 |

→ **legacy 구멍이 배포 후 7일 뒤 운영자 조치 없이 자동으로 닫힌다.** 남는 PENDING은 기존
`scripts/backfill-pending-match-results.mjs`가 운영자 확인 아래 처리(현행 잔여 처리와 동일).

**matchId 없는 기록:** `:69` / `:209`의 조기 반환은 **건드리지 않는다**. 로스터 조회 이전이므로
설계상 자동 보존. (다만 §0-1 문 B 참고.)

## 4. 대안: 엄격 변형 (legacy 폴백 없음)

`legacy` 칸을 없애고 **로스터 없으면 무조건 PENDING**.

- 장점: 재현된 구멍이 **배포 즉시** 닫힌다. 결정 표가 2줄로 단순해지고 epoch 필드가 필요 없다.
- 대가 1: 배포 직전 7일 내 매치의 늦은 저장이 PENDING으로 남아 스크립트 처리 대상이 된다.
  (현재 규모에선 소수 — 아마 0~수 건.)
- 대가 2: **기존 계약 테스트 1건이 깨진다.** `runningMatchContract.test.mjs:2760`
  "both 1v1 party-run devices claim a local win…"은 세션도 로스터도 없는 스토어에서
  no-session 분기가 **해소되기를** 기대한다. 테스트를 `createMatchSession` 경유로 다시 짜거나
  로스터를 심어야 한다.

**판단:** 오너가 "기존 동작 보존이 기본"이라고 못 박았고, 재현된 공격은 **피해자의 matchId를 알아야**
성립한다(파티룸 멤버·친구 기록 상세로 노출되긴 하나 무작위 대량 공격은 아니다). 그래서
**§3의 epoch 방식을 추천**한다 — 계약을 지키면서 7일 뒤 자동으로 엄격해진다.
다만 오너가 "구멍이 영구 오염을 만드니 7일도 못 기다린다"고 판단하면 **§4로 전환**하는 것도 합리적이다.
**이건 오너 결정 사항이다.**

## 5. 완주 판정 강화 (DNF가 완주자를 못 이기게)

로스터 게이트는 **침입자**를 막지만 **케이스 2b**(진짜 상대가 일찍 포기 → 낮은 경과시간으로 승리)는
그대로 남는다. 정당한 참가자가 저지르는 치팅이므로 보안 사안이기도 하다.

`isTrustworthyMatchEvidence`(`matchResultBuilders.mjs:862`, 이미 존재)를 재사용:

- **정렬 규칙:** 신뢰 가능 완주자 그룹을 먼저, 그 안에서 경과시간 오름차순. 비신뢰(DNF/차량)는 뒤로.
- **듀얼에서 상대가 비신뢰일 때:** `win`(완주자 승) vs `PENDING` 중 → **`win` 추천.**
  라이브 세션의 §B4 폴백이 이미 "DNF는 패배"로 판정하므로 **양쪽 경로가 같은 답을 낸다**(패리티).

**커밋 분리 여부 → 별도 커밋(2번째) 추천.**
1번 커밋은 "누가 참가자로 계수될 수 있는가"만 바꾸고, 2번 커밋은 "로스터가 검증된 정당한 매치의
승패 순서"를 바꾼다 — 후자는 **정상 매치의 판정을 바꾸는 실질 행동 변화**라 되돌림 단위와
변이 검증 대상이 달라야 한다. **푸시는 두 커밋 함께.**

**§0-1 문 A(비참가자 자가 지급)** 는 1번 커밋에 포함 권장 — 같은 파일·같은 계열·1줄이고,
로스터 게이트가 no-session에서 하는 것과 **정확히 같은 처리**를 세션 분기에서도 하게 만드는 일관성 수정이다.

## 9. 구현 결과

### 9-1. 최종 형태

새 파일 `backend/src/lib/matchRosters.mjs` + 판정 경로 수정. 소비는 `collectSavedMatchRuns` 한
길목에 로스터 필터를 넣어 듀얼 resolver·그룹 resolver·GET /result 세 곳을 동시에 덮었다.
resolver의 5번째 인자는 `options` 객체(`{ savingRun, rosterOverride }`)로 정리했다.

로스터 항목 실측 크기: **듀얼 147바이트 / 30인 그룹 598바이트** → 상한 5,000건 최악 ≈ **718KB**.
(설계 시 추정 110바이트는 낙관적이었다. 상수 주석을 실측값으로 고쳤다.)

### 9-2. 설계에 없던 자체 발견 결함 — 운영자 복구 경로가 막혔다

설계는 잔여 PENDING의 처리를 `scripts/backfill-pending-match-results.mjs`에 맡긴다. 그런데 그
스크립트가 다루는 대상이 바로 **세션도 내구 로스터도 없는 옛 매치**다 — epoch가 성숙하면 게이트가
그걸 전부 거절하므로, **탈출구 자체가 조용히 막힌다.** 실행으로 확증했다(성숙 전 `["host","guest"]`
치유 → 성숙 후 `[]`, 블롭은 PENDING 그대로).

수정: `backFillSavedRunsForMatchId`가 호출자의 **이미 검증된 명단**을 `options.rosterOverride`로
resolver까지 내려보낸다. 내구 로스터가 있으면 그쪽이 우선(서버가 만든 값이고 목표 거리도 들고 있다).
세션 기반 호출자는 세션이 살아 있어 이 값을 쓰지 않는다. 회귀 테스트 2건 추가.

### 9-3. 오너 지적(comparedDistanceKm 동결) 처리 — 제안한 보조 신호는 채택하지 않았다

**채택한 것:** 목표 거리를 **로스터에 박제**하고(`session.distanceKm`, 세션 생성 시점 = 달리기가
시작되기도 전에 서버가 정한 값) `isTrustworthyMatchEvidence(run, goalDistanceKm)`가 그걸 쓴다.

**오너 제안(두 기록의 실측 distanceKm 직접 비교)을 안 쓴 이유:**
- 로스터 목표는 **절대 기준**이고 상대 비교는 아니다 — "둘 다 완주"와 "둘 다 미완주"를 구분할 수
  있어야 하는데, 상대 비교로는 그게 안 된다(둘 다 포기해도 더 멀리 간 쪽이 "완주자"가 된다).
- 얼거나 위조될 여지가 없다. 상대 비교는 GPS 오차가 큰 쪽이 이기는 새 편향을 만든다.
- 로스터가 없어 목표를 모르는 경우(legacy)에는 **완주 판정을 아예 시도하지 않고** 기존 경과시간
  비교를 유지한다 — 얼어붙은 값으로 판정하느니 기존 동작이 안전하다. 즉 보조 신호가 필요한 자리가
  남지 않는다.

동결 시나리오는 전용 테스트로 못 박았다("a FROZEN comparedDistanceKm cannot disguise a quitter as
a finisher": 중도포기자의 compared가 1.2로 얼어 `goalKm == distanceKm`이 되는 케이스).

### 9-4. 남긴 것 (의도적 범위 밖)

**둘 다 미완주(both-DNF)일 때는 여전히 먼저 그만둔 쪽이 이긴다.** 완주자 대 미완주는 고쳤지만,
양쪽 다 목표를 못 채웠을 때의 순서는 건드리지 않았다 — 정상적으로 둘 다 일찍 멈춘 대결(실사용에서
흔하다)의 판정을 오너 승인 없이 뒤집게 되기 때문이다. 파티런은 `matchGoalDistanceKm` 게이트가
이미 보너스를 0으로 만들지만, `source:'official'`에는 그 게이트가 없다. **백로그 후보.**

## 10. 백로그 등록 항목 (오너 지시 3번)

**문 B — matchId 없는 매치 블롭이 클라가 주장한 `resultTone:'win'`으로 +20P를 무한 수확한다.**

- 현상: `matchResultBuilders.mjs`의 `matchId` 부재 조기 반환(듀얼 `:75`, 그룹) 뒤 블롭이 그대로
  저장되고, `getMatchBonusPoints`는 저장된 `resultTone`만 보고 지급한다. 저장 횟수 제한이 없다.
  `source:'party'`는 2026-08-06 목표거리 게이트가 막지만 `source:'official'`은 무방비이고,
  `source`도 클라가 정한다.
- **설계 메모(오너 지시):** 이번에 넣은 **epoch 장치로 그대로 닫을 수 있다.** "matchId 없는 기록
  무변경" 계약의 취지는 구형 클라 호환이고 현행 클라는 전부 matchId를 보내므로,
  `isMatchRosterEpochMature(store, now)`가 참일 때 **epoch 이후 신규 저장 중 matchId 없는 매치
  블롭 → PENDING`으로 좁히면 계약과 충돌하지 않는다. 구형 클라의 옛 기록은 epoch 이전이라 그대로다.
- 주의: 판정이 아니라 **포인트 정책**을 건드리는 변경이라 별도 검증 라운드가 필요하다.

## 11. 적대 검증 라운드 결과 (SHIP-WITH-FIXES → 수정 반영 완료)

5개 렌즈(우회·회귀·수명주기·언어의미·완주규칙) 독립 탐색 → 발견마다 독립 반박자 → 최종 판정.
원시 24건 → 검증 8건 → 생존 5건. **must-fix 2건은 반영 완료**, 나머지는 §12 추적 항목.

### 11-1. 반영한 must-fix

**(A) prune을 사이에 둔 대결에 승자가 둘 생긴다.** 완주 우선 규칙은 세션 없는 경로에만 있고 라이브
경로에는 없다(라이브는 경과시간만 보고, 목표 미달 `status:'finished'`도 그대로 받는다 —
`matchActionHandlers.mjs:196`). 두 저장이 10분 prune을 사이에 두고 갈리면 각자 다른 답이 확정으로
박제된다. **실행으로 확증: quitter win 20P + finisher win 20P = 한 대결에 40P.** 순서를 뒤집으면 둘 다
lose. 둘 다 '확정'이라 never-downgrade 가드가 영구 고정한다.

수정: 상대 블롭이 이미 **서버가 확정한** 판정을 들고 있으면 그 거울을 내 판정으로 삼는다
(`mirrorOpponentSealedOutcome`, 완주 우선보다 먼저).

> **원안 그대로 쓰지 않았다.** 검증이 제안한 무조건 mirror에는 구멍이 있다 — 기권 블롭은 세션 없는
> 경로에서 **서버 검증 없이 그대로 통과**하므로 그 `resultTone`은 클라가 정한 값이다. 무조건
> 거울로 삼으면 한쪽이 `기권승`을 주장하는 것만으로 상대 기록이 패배로 뒤집힌다. 통과 사실을
> 실행으로 확인하고 **기권 블롭을 거울에서 제외**했다(전용 테스트 + 변이 M13).

**(B) 로스터 보존기간의 시계가 '러닝'이 아니라 '매칭'에서 시작한다.** 매칭은 두 러너가 짝지어진 즉시
세션을 만들고, 슬롯은 최대 `MATCH_BOOKING_WINDOW_DAYS`(7일) 뒤다. 여기에 클라 저장 대기열 7일이
붙으므로 최악의 정당한 늦은 저장은 14.04일 — 14일 보존을 넘겨 진짜 승자가 0P PENDING으로 굳는다
(계약 #2 위반). 수정: `RETENTION = (MATCH_BOOKING_WINDOW_DAYS + 14)일 = 21일`.
`createdAt`을 slotStartAt으로 옮기면 시간 단조성이 깨져 prefix-drop GC가 무너지므로 보존기간을 늘렸다.

### 11-2. 추가로 반영한 것 (검증은 추적 등급으로 분류했으나 내 변경이 만든 불일치라 같이 고침)

**운영자 스크립트의 드라이런과 집행부가 서로 다른 목표 거리를 봤다.** 집행부는 로스터 목표로
판정하게 바뀌었는데 드라이런(`findUntrustworthyRuns`)은 여전히 블롭의 `comparedDistanceKm`을 읽어,
"막을 게 없다"고 해놓고 집행은 거절하는 **조용한 거짓 초록**이 됐다. 로스터 목표를 드라이런까지
연결했다. 덤으로, `comparedDistanceKm`을 아예 안 싣는 그룹 블롭의 거짓 blocker도 사라진다.

## 12. 추적 항목 (이번에 안 고침 — 오너 판단)

1. **라이브 아레나가 목표 미달 `status:'finished'`를 완주로 받는다**(`matchActionHandlers.mjs:196`).
   (A)의 진짜 뿌리. 라이브 거리는 화면 꺼짐에 얼어붙으므로 여기에 목표 게이트를 다는 것은 진짜
   완주자를 DNF로 봉인할 위험이 있다 — **별도 설계 라운드 필요.** 거울 수정이 그동안 피해를 가둔다.
2. **그룹 쌍둥이:** 새 `completed` 정렬 키가 라이브 `buildGroupVerdict`에는 없어, prune을 걸친
   그룹은 여전히 모순된 순위(1위 두 명)가 가능하다. 듀얼의 거울 수정이 그대로 이식되지 않는다
   (거울로 삼을 단일 상대 tone이 없다). **미실행 — 확인 필요.**
3. **`backFillSavedRunsWithVerifiedRoster`가 로스터 전원 완주를 요구**해, commit 2가 존재하는 이유인
   완주자 vs 중도포기 매치를 스크립트가 거절한다. 그 스크립트의 원래 설계 의도(전원 완주자)와
   충돌하므로 규칙 완화는 오너 결정 사항.
4. **`backFillMatchCounterpartSavedRuns`는 라이브 세션이 없으면 조기 반환** — 두 저장이 10분 prune을
   걸치면 먼저 저장한 쪽의 PENDING이 자동 치유되지 않는다(잔여 승자-0P 형태). 이번 변경이 만든
   것은 아니지만 치유 서사 전체가 라이브 세션에 의존한다.
5. **그룹 no-show:** 로스터 전원이 저장해야 봉인되므로 한 명이 영영 저장하지 않으면 봉인되지 않는다
   (세션 없는 경로에는 §B4 같은 시한 폴백이 없다). 과소보고 케이스는 승인받았으나 no-show는 별건.
6. **둘 다 미완주(both-DNF)** 순서는 그대로(먼저 그만둔 쪽 승). §9-4 참조.
7. **`wipePrelaunchDataTransform.mjs`가 `matchRosters`/`matchRosterEpochAt`를 안 지운다.**
   무해하지만(고아 로스터는 만료되고 빈 집합만 거른다) 일관성 차원에서 추가 권장.
