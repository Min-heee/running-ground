# 화면을 끈 채 달린 구간이 기록에서 통째로 빠진다

**한 줄 요약** — 거리 원장이 JS와 네이티브 둘로 갈라져 있었고, **저장되는 기록은 100% JS 원장**인데 iOS는 화면이 꺼지면 JS 스레드를 재운다. 네이티브 누적기가 옆에서 정확히 센 거리는 업로드 페이로드에만 실려, 저장 경로에는 끝내 도달하지 못했다.

---

## 증상

두 번의 실기기 사고가 같은 뿌리에서 나왔다.

**1) 2026-08-09, 실기기 1:1 대결.** 갤럭시의 거리가 3.05km에서 굳었다. 굳은 값이 상대 아이폰 화면에도 그대로 3.05km로, 그것도 "연결됨" 상태로 표시됐다. 화면을 켜는 순간에만 값이 따라잡혔다.

**2) 2026-08-17, 파티런(실사고).** 한 사용자가 아이폰(스토어 빌드 55)으로 화면을 끄고 달렸다. 같은 코스를 이전보다 더 빠르게 뛰었는데, 저장된 기록은 목표 5km에 못 미친 채 끝났다. 상대 화면에서는 중간에 얼어붙어 보였다.

증상이 둘로 갈라져 보인 게 진단을 늦췄다. 하나는 "**상대 화면이 안 움직인다**"(라이브 표시 문제로 보였고), 다른 하나는 "**내 기록이 짧다**"(측정 정확도 문제로 보였다). 실제로는 같은 원장이 얼어붙은 결과였다.

### 재현 조건

| 조건 | 값 |
|---|---|
| 플랫폼 | iOS에서 확정적(화면 꺼짐 = JS 스레드 정지). Android는 JS가 살아 픽스를 받으면서도 전부 필터에 거절돼 **거리만 어는** 변형으로 나타남(8/9 갤럭시) |
| 화면 | 러닝 중 화면을 끄거나 잠금 (앱을 종료할 필요 없음) |
| 위치 권한 | "항상"이어도 재현됨 — 권한은 **배달**을 보장할 뿐 **처리**를 보장하지 않는다 |
| 지속 시간 | 잠든 구간이 길수록 손실이 그대로 비례 |
| 결과 | 저장 기록에서 잠든 구간이 통째로 누락. 라이브에서는 상대에게 정지로 보임 |

두 변형의 공통분모는 플랫폼이 아니라 **얼어붙은 JS 원장**이다. 얼리는 원인만 둘(스레드 정지 / 전량 필터 거절)이고, 그 아래는 같은 결함 하나다.

## 처음 의심한 것 (그리고 왜 틀렸나)

이 사고는 두 달에 걸쳐 **다섯 번 오진**했다. 매번 고쳤고, 매번 증상이 남았다. 순서대로 적는다.

### 가설 A — "업로드 케이던스 문제다"

첫 진단은 이랬다. 상대 화면이 안 움직이는 건 내 폰이 서버에 진행을 안 올리기 때문이다. 실제로 업로드 방아쇠 세 개 중 둘(1초 setInterval, 3초 setInterval)이 백그라운드에서 죽고, 살아남는 건 GPS 픽스가 배달될 때마다 도는 위치 태스크 콜백뿐이었다. 그래서 **네이티브 업로더**를 만들었다 — Kotlin은 포그라운드 서비스 안에서 3초 틱, Swift는 GPS 배달을 방아쇠 삼아 같은 3초 스로틀로 재전송.

**반증**: 네이티브 업로더가 실제로 도는 빌드를 깔고 다시 뛰었는데도 얼어붙었다. 이유는 코드 주석에 이미 적혀 있었다 — *네이티브 쪽은 거리/페이스/경과를 절대 재계산하지 않는다.* 마지막 JS 페이로드를 **바이트 그대로** 재전송할 뿐이다. JS가 자면 얼어붙은 숫자를 3초마다 성실하게 다시 올린다. 케이던스는 문제의 절반도 아니었다.

> **곁가지 오진 하나** — 그 사이 "iOS는 원래 안 된다(OS 한계)"는 결론을 내리고 있었는데, 나중에 보니 iOS 네이티브 업로더는 **애초에 링크조차 안 되고 있었다.** 로컬 Expo 모듈의 podspec이 `:ios => '16.4'`로, 앱 배포 타깃(15.1)보다 높아서 autolinking의 `supports?` 검사가 실패하고 pod을 조용히 건너뛰었다(`4b99d4d8`). "OS 한계"라는 판단이 *실행되지도 않은 코드*를 근거로 서 있었다. 교훈은 하나다 — **어떤 경로가 안 된다고 결론 내리기 전에, 그 코드가 실제로 실행되고 있는지부터 증명한다.**

### 가설 B — "위치 권한을 '항상'으로 주면 된다"

**반증**: 권한을 "항상"으로 준 폰에서 그대로 재현됐다. 진단을 끝낸 건 페이스 숫자였다. 화면을 끈 구간에서 평균 페이스가 `13:02/km`까지 치솟았다가 화면을 켜는 순간 `5:35`로 스냅백했는데, 평균 페이스는 누적 `경과 ÷ 거리`라 **아무리 빨리 달려도 그렇게 못 내려온다.** 그건 빨라진 게 아니라, 얼어붙었던 분모가 한꺼번에 되돌아온 자국이었다. 즉 GPS 픽스는 도착하고 있었고, 그걸 거리로 바꾸는 코드가 안 돌고 있었다. (이 스냅백을 화면에서 감추는 임시 조치가 `eb69c084` — 표시를 고쳤을 뿐 얼어붙음은 그대로였다.)

### 가설 C — "네이티브 거리 누적기를 만들면 끝난다"

여기서 진짜 재료가 만들어졌다. iOS/Android 양쪽 네이티브에 JS의 필터 체인(정확도·나이·냉시동 워밍업·최소 시간차·순간이동 게이트·정지 노이즈·거리 게이트)을 그대로 미러링한 거리 누적기를 넣었다. JS가 자도 거리는 네이티브에서 계속 늘었다.

**절반만 맞았다.** 병합 방식을 의도적으로 가장 보수적인 것으로 골랐기 때문이다 — **업로드 페이로드에만** 병합했고, 스냅샷과 UI와 저장 경로는 손대지 않았다. 네이티브 누적기는 JS의 경로 **재작성** 패스(냉시동 이탈 붕괴, 지터 붕괴)를 갖지 못해 과다 계상할 수 있고, 그런 값으로 완주 판정이 나면 경쟁 무결성이 깨진다는 판단이었다.

그 판단 자체는 지금도 옳다고 본다. 문제는 **그래서 사용자가 잃는 것이 무엇인지**를 다시 보지 않은 것이다. 라이브 화면은 나아졌지만, 사용자가 실제로 잃고 있던 건 **저장되는 기록**이었고 그 경로에는 여전히 아무 변화가 없었다.

### 가설 D — "신선도 판정은 잘 돌고 있다" ← 이 글의 첫 번째 핵심

네이티브 값으로 갭을 메우는 경로에는 게이트가 하나 있었다. *"내 거리가 지금 정지 상태인가"* — 정지일 때만 네이티브 값을 쓰고, 살아 있으면 JS가 이긴다(fresh-JS-wins). 합리적이다. 그런데 그 판정이 이렇게 걸려 있었다.

```ts
// src/features/runs/tracking/background/backgroundMatchProgressSync.ts (수정 전)
const isMyDistanceStaleNow = isMyMatchDistanceStale({
  lastUpdatedAtMs: getBackgroundSyncDiagnostics().lastSnapshotAtMs,
  nowMs,
});
```

`lastSnapshotAtMs`는 **스냅샷이 커밋된 시각**이다. 그리고 `routeAccumulator`는 정확도 초과로 **버린** 픽스(DROP acc-high)에도 `commitSnapshot`을 부른다 — 페이스와 경과 시간은 갱신되니까. 커밋될 때마다 `lastSnapshotAtMs`는 무조건 찍혔다.

결과:

- 거리는 1m도 안 느는데 **영원히 "fresh"**로 읽힌다.
- 그래서 화면 꺼짐용 네이티브 갭필이 **한 번도 안 켜진다.**
- 게다가 매 flush마다 "JS가 살아 있으니 기준선을 맞추자"며 네이티브 누적값을 **얼어붙은 JS 값으로 되돌려 지웠다.**

즉 **안전장치가 스스로를 잠그고, 증거까지 지우고 있었다.** 코드는 정확히 설계대로 동작했다. 틀린 건 정의였다. "신선도"가 *"우리는 여전히 측정 중인가"*를 뜻해야 하는데 실제로는 *"센서에서 뭔가 들어왔는가"*를 뜻하고 있었고, 화면 꺼짐 정지는 정확히 그 둘 사이 틈에 살고 있었다.

정의를 바꿨다 — `lastDistanceAdvanceAtMs`. **거리가 실제로 늘었을 때만** 찍는다.

```ts
// src/features/runs/tracking/background/snapshotStore.ts
// 상태를 갈아끼우기 전에 비교한다: 필터가 거부한 픽스도 여기 도착하지만
// (갱신된 페이스를 싣고) distanceKm은 그대로다.
const previousDistanceKm = Number.isFinite(snapshotState.distanceKm) ? snapshotState.distanceKm : 0;
const nextDistanceKm = Number.isFinite(snapshot.distanceKm) ? snapshot.distanceKm : 0;
const distanceAdvanced = nextDistanceKm > previousDistanceKm;

setSnapshotState(snapshot);
recordBackgroundSnapshotUpdate(distanceAdvanced);
```

같은 커밋(`cef20352`)에서 **서버 쪽 대칭 결함**도 나왔다. 안드로이드 네이티브 업로더가 같은 페이로드를 3초마다 재전송하는데, 서버는 그 재전송마다 `liveUpdatedAt`을 다시 찍고 있었다. 정지 감지가 영원히 안 울리고, 상대 폰은 굳은 숫자를 **자신 있게 "연결됨"으로** 그렸다. 고침은 원본 페이로드 시그니처(`distanceKm|elapsedSeconds|status`)로 재전송을 식별해, 동일 페이로드는 생존 시계를 건드리지 않는 것.

두 가지가 중요했다.
- **정규화된 값이 아니라 원본으로 비교해야 한다.** 서버가 `elapsedSeconds`를 자기 벽시계로 덮어쓰기 때문에, 정규화 후에는 재전송도 매번 새 값으로 보인다. 재전송은 기기가 실제로 보낸 바이트에서만 보인다.
- 판별 기준은 *"움직였나"*가 아니라 ***"새 정보인가"***다. 신호등에 서 있는 러너는 JS가 살아 `elapsedSeconds`가 계속 바뀌므로 그대로 "연결됨"을 유지한다.

### 가설 E — "고쳤으니 켜면 된다"

신선도 정의를 고친 그날(커밋은 새벽 1시 38분이었다), 적대 검증이 13건을 제기해 3건이 살아남았고 그중 하나가 critical이었다. **네이티브 누적기에는 JS의 신호 끊김 갭 규칙이 없다.** JS는 픽스 간격이 30초를 넘으면 그 구간의 직선을 "우리가 본 경로가 아니다"로 보고 0m 처리하고 앵커만 옮긴다. 그런데 Kotlin/Swift `consume()`에는 dt 상한이 아예 없었다. 터널이나 지하철 3분이면 약 1km의 직선이 통째로 적립되고, 서버는 `Math.max(previousDistanceKm, …)`라 **한 번 오른 값을 영원히 못 내린다.**

여기서 반직관적인 부분: **속도 필터는 이걸 못 막는다.** 끊긴 시간이 길수록 그 직선의 암묵 속도는 **낮아진다.** 3분에 990m는 지극히 그럴듯한 러닝 속도라 순간이동 게이트도, 서버의 속도 기반 규칙도 전부 통과한다.

그리고 방금 한 수정이 **이 경로를 훨씬 자주 열어준다**는 게 문제였다. 기존에는 JS가 완전히 잠긴 경우에만 갭필이 열렸는데, 정지 판정을 넓히면 "신호가 계속 거부되는 구간"과 "긴 정지 구간"까지 포함된다.

그래서 신호는 계산하되 **소비를 플래그 뒤로 격리**했고(`a2a3d67c`, 기본 false), 네이티브 양쪽에 갭 규칙을 이식했다(`35b70a34`). 위치는 순간이동 게이트보다 **앞**이어야 했다. 뒤에 두면, 직선이 순간이동 게이트에 걸릴 때 그 게이트는 앵커를 안 옮기고 픽스만 버리므로 갭 검사가 영영 실행되지 않고 **남은 러닝 내내 거리가 얼어붙는다.** 갭 우선이면 적립 거부와 재앵커를 동시에 한다.

```swift
// modules/match-progress-uploader/ios/MatchProgressUploaderModule.swift — DistanceAccumulator.consume()
// 갭 규칙은 양쪽 순간이동 게이트보다 앞. 속도 기반 게이트는 여기서 방어가 안 된다.
if let maxCreditableFixGapMs = maxCreditableFixGapMs, dtMs > maxCreditableFixGapMs {
  lastAppended = current
  lastCounted = current
  return nil          // 적립 거부 + 양쪽 앵커 이동
}
```

### 가설 F — "갭 규칙 빌드가 최소 배포 버전이 되면 켠다" ← 마지막이자 가장 값비싼 오진

플래그를 켜는 조건을 **함대 조건**으로 걸었다. *"갭 규칙을 담은 빌드가 최소 배포 버전이 되면 켠다."*

**앱에는 최소 버전 강제가 없다.** 구버전 설치가 하나라도 살아 있는 한 그 날은 **오지 않는다.**

8/17 사고 당시, 그 사용자의 아이폰은 이미 빌드 55 — 갭 규칙을 담은 바이너리였다. 고칠 코드는 전부 그 폰 안에 있었는데, 함대 전체를 기다리는 플래그 때문에 꺼져 있었다. 조건을 **기기별 판별**로 바꾸는 것이 답이었다: 조건이 함대가 아니라 **그 폰**에 대한 것이 되면, 새 바이너리는 오늘 고쳐지고 옛 바이너리는 오늘과 똑같이(더 나빠지지 않게) 동작한다.

## 진짜 근본 원인

구조를 한 장으로 적으면 이렇다.

```
GPS 픽스
   ├─▶ [JS 원장] appendTrackedLocation → accumulatedDistanceMeters → snapshot.distanceKm
   │        └─▶ 화면 표시 · 완주 판정 · 서버 업로드 · ★저장되는 기록★
   │        ✗ iOS 화면 꺼짐 = JS 스레드 정지 = 이 줄 전체가 안 돈다
   │
   └─▶ [네이티브 원장] DistanceAccumulator (Swift/Kotlin)
            └─▶ 업로드 페이로드의 distanceKm 병합에만 사용
            ✗ 저장 경로로 가는 길이 아예 없다
```

세 문장으로 요약된다.

1. **저장되는 기록의 유일한 출처는 JS 원장이다.**
2. **iOS는 화면이 꺼지면 JS 스레드를 재운다.** GPS는 계속 배달되지만 그걸 거리로 바꾸는 코드가 안 돈다.
3. **네이티브 원장의 정확한 값은 업로드에만 실렸다.**

그래서 잠든 구간은 *라이브에서만 부분적으로 보이고, 기록에서는 영원히 사라졌다.* 그 위에 자물쇠 두 개가 더 채워져 있었다 — 스스로를 잠그는 신선도 정의(가설 D), 오지 않는 날에 걸린 함대 게이트(가설 F).

그리고 마지막 제약 하나가 설계를 규정했다. **증거는 깨어나는 순간 파괴된다.** 앱이 전면으로 돌아오면 배터리를 위해 네이티브 누적기를 즉시 끄고, 그 순간 네이티브 총거리는 사라진다. 즉 **깨어나는 그 한 순간이 유일한 창**이다.

## 해결

### 1) 함대 조건 → 기기별 바이너리 판별

[`src/features/runs/tracking/background/nativeGapRuleSupport.ts`](../../src/features/runs/tracking/background/nativeGapRuleSupport.ts) — 설치된 **바이너리의 빌드 번호**로 판별한다(iOS ≥ 55, Android ≥ 44 = 갭 규칙 커밋을 담은 첫 빌드). OTA 번들의 `app.json` 숫자는 구버전 기기에서도 최신을 말하므로 증거가 못 된다.

판별 불가(빌드 번호 없음·숫자 아님·미지의 플랫폼)는 전부 **false**다. 이 신호가 여는 것은 부정 적립 가능성이 있는 경로라, 모르면 닫는 쪽이 안전하다(fail-closed).

> 적대 검증이 여기서 P0을 하나 잡았다. 처음엔 `expo-constants`의 `nativeBuildVersion`을 읽었는데 **해당 버전에는 그 값이 없다.** 래치가 영원히 false로 남아 기능 전체가 조용히 죽는 상태였다. `expo-application`의 값으로 교체하고 직속 의존성으로 못 박았다. — *fail-closed 기본값은 이런 실수를 "안전하게 아무것도 안 하는 상태"로 바꿔주지만, 동시에 **완전한 침묵**으로도 바꾼다.*

### 3) 적대 검증 19건 → **판별을 없애는 재설계** (`85cf363e`) ← 이 글의 두 번째 핵심

병렬 에이전트 30개로 돌린 적대 검증에서 **P0 2건 포함 19건**이 확정됐다. 그중 두 건이 1차 설계의 재생 판별을 직접 겨눴다.

- **P2 — 부분 재생 이중 적립**: OS가 밀린 픽스를 *일부만* 재생하면, "재생 아님"으로 판정돼 전액 크레딧이 나가고 재생된 몫이 두 번 적립된다.
- **P1 — 전량 몰수 과소 적립**: 반대로 "재생됨"으로 판정하면 크레딧을 통째로 버리는데, 나이 필터(15초)가 오래된 픽스를 대부분 떨어뜨리므로 JS는 실제로는 거의 못 따라잡는다.

재생 판별을 **더 정확하게** 만들 수도 있었다. 대신 뺄셈의 기준점을 옮겼다.

| | 1차 설계 (`2ad10df8`) | 2차 설계 (`85cf363e`) |
|---|---|---|
| 크레딧 공식 | 포획 네이티브 − **포획 시점**의 JS | 포획 네이티브 − **정산 시점**의 JS |
| 재생 처리 | 타임스탬프로 판별 → 재생이면 전량 폐기 | **판별 없음** |
| 부분 재생 | 이중 적립 (P2) | 되찾은 몫이 자동 차감 |
| 전량 재생 | 전량 몰수 → 과소 적립 (P1) | 차이가 0으로 수렴 → 크레딧 0 |
| 정산 시점 | 첫 묶음 **처리 전** | 첫 묶음 **반영 후** |

```ts
// src/features/runs/tracking/background/screenOffGapReconcile.ts — settle()
const jsMetersNow = getAccumulatedDistanceMeters();          // ★ '지금'의 JS
const rawCreditMeters = gap.nativeMetersAtWake - jsMetersNow;
const capMeters = (gap.staleGapMs / 1000) * MAX_REASONABLE_RUNNING_SPEED_MPS;
const creditMeters = Math.min(rawCreditMeters, capMeters);

if (creditMeters < MIN_CREDIT_METERS) { /* 지터 바닥 미만 — 안 준다 */ return; }
creditExternalDistanceMeters(creditMeters);
```

핵심은 이것이다. **OS가 밀린 픽스를 재생하든, 마지막 15초 꼬리만 배달하든, JS가 스스로 되찾은 거리는 정산 시점의 JS 총거리에 이미 들어 있다.** 빼는 쪽이 자동으로 맞춰지므로 재생을 판별할 필요 **자체가 없어진다.** 정산 모듈은 순 11줄 줄었지만(218→207) 중요한 건 줄 수가 아니라 **사라진 것들**이다 — 재생 판별 블록 전체, 상태 하나(`jsMetersAtWake`), 상수 하나(`REPLAY_DETECT_TOLERANCE_MS`), `settle()`의 인자 둘, 그리고 서로 반대 방향의 오적립 두 종류.

이 재설계가 파생시킨 나머지 수정들:

| 수정 | 이유 |
|---|---|
| 정산을 첫 묶음 **반영 후**로 이동 | 반영 전에 정산하면 재생 몫이 두 번 적립된다 (뺄셈의 전제가 깨짐) |
| 포획 문턱을 45초로 (= 신호끊김 30초 + 15초) | 30초 미만 공백은 라이브 필터가 직선을 **정상 적립**한다 — 거기 크레딧까지 주면 이중 |
| 일시정지 상태에서도 정산 허용 | 깨어나자마자 종료 버튼을 누르는 것이 **바로 이 사고의 실제 흐름**이었다. 그때 스냅샷은 이미 `paused` |
| 저장 커맨드가 스냅샷을 읽기 전에 강제 정산 | 픽스도 12초 타이머도 오기 전에 저장이 시작될 수 있다 |
| 재포획 전에 기존 포획 먼저 정산 | 잠금화면 배너·Face ID로 `active`가 연달아 오면, 버린 포획은 이미 꺼진 네이티브에서 다시는 알 수 없다 |
| 전면 위치 워치에도 정산 훅 | 전면에서는 백그라운드 태스크가 안정적으로 안 울려 타이머까지 기다리며 과소 적립됐다 |

정산 방아쇠는 최종적으로 다섯 개다: **첫 픽스 반영 후**(백그라운드 태스크 + 전면 워치), **12초 타이머**(실내에서 끝내는 경우), **저장 직전 강제**, **일시정지/정리 시**, **재포획 직전**.

### 4) 크레딧은 별도 원장에 든다

`accumulatedDistanceMeters`는 두 곳(냉시동 이탈 붕괴·지터 붕괴)에서 **경로로부터 통째로 재계산**된다. 크레딧 구간은 경로에 점이 하나도 없으므로, 합산에 안 실으면 **다음 커브 하나에 되찾은 거리가 소리 없이 지워진다.** 그래서 `externalCreditMeters`를 따로 들고 재계산 결과에 더한다. 크래시 복원 파일에도 같은 이유로 몫을 싣는다(옛 파일에는 없던 필드 → 0으로 읽는다).

그리고 적대 검증의 나머지 P0이 여기 있었다. **잠든 구간의 직선이 경로에는 남아 있다.** 경로 기반 재계산은 원시 하버사인 합이라 그 직선을 크레딧과 **함께** 적립한다.

```ts
// src/features/runs/tracking/background/routeAccumulator.ts — sumObservedRouteDistanceMeters()
// 실제로 관측한 구간만 합산한다 — 신호 끊김 갭(>30s)의 직선은 우리가 본 경로가 아니다.
for (let index = 1; index < route.length; index += 1) {
  const previousMs = resolveRoutePointTimestampMs(route[index - 1]);
  const nextMs = resolveRoutePointTimestampMs(route[index]);
  if (previousMs !== null && nextMs !== null && isSignalLossGapMs(nextMs - previousMs)) continue;
  distanceMeters += calculateDistanceBetweenPoints(route[index - 1], route[index]);
}
```

이건 크레딧이 없어도 존재하던 **선재 결함**이기도 했다 — 잠든 구간의 직선이 재계산 한 번에 통째로 되살아나던 길이 원래 열려 있었다.

### 5) 마지막 이중 적립 경로 — 정산 후 수면 꼬리 (`317623fa`)

재검증에서 하나 더 나왔다. 깨어나기 직전 ~15초의 픽스는 나이 필터를 통과할 수 있어서, 정산이 그보다 먼저 확정되면 크레딧에도 들어 있고 뒤늦게 원장에도 적립됐다(기록상 깨어남당 최대 ~127m, 통상 30–60m). 정산이 확정되는 순간 `routeAccumulator`에 **'깨어난 시각' 바닥**을 놓아 그 이전 시각의 픽스를 차단한다. 정산 전에 도착한 꼬리는 이미 '지금의 JS'에 들어 있어 뺄셈이 차감한다 — **도착 순서와 무관하게 정확히 한 번만 센다.**

### 고르지 않은 대안

| 대안 | 왜 안 골랐나 |
|---|---|
| 저장 기록을 네이티브 값으로 대체 | 네이티브는 JS의 경로 **재작성** 패스(냉시동 이탈·지터 붕괴)를 못 갖는다 — 전체 경로 이력이 필요한데 네이티브는 안 들고 있다. 과다 계상이 곧 완주 판정 오염이 된다 |
| "화면을 켜세요" 안내 강화 | 이미 있었고 사고를 못 막았다. 사용자에게 OS 제약을 대신 지게 하는 방식 |
| 재생 판별을 더 정확하게 | 정확해질수록 복잡해지고, 부분 재생은 원리적으로 못 가른다 (위 표) |
| 함대 최소 버전 강제 도입 | 사고 당일의 손실을 못 되돌린다. 기기별 판별이 같은 안전성을 즉시 준다 |

## 검증

**적대 검증.** 병렬 에이전트 30개로 돌린 적대 검증에서 **P0 2건 포함 19건**이 확정돼 전부 수정됐다. 재검증은 4렌즈(이중 적립·손실·래치·회귀)로 돌렸고 **3개는 코드 추적까지 통과, 남은 이중 적립 렌즈가 수면 꼬리 결함을 하나 더 잡아** 위 5번으로 봉쇄했다. 여기서 나온 P0 두 건(`nativeBuildVersion` 부재로 인한 조용한 사망, 잠든 직선의 경로 재계산 이중 적립)은 **둘 다 단위 테스트로는 절대 안 잡히는 종류**였다 — 하나는 라이브러리 API 사실관계, 하나는 두 서브시스템의 교차점.

**단위 테스트가 고정하는 계약** (`screenOffGapReconcile.test.ts`, 13개):

| 테스트 | 고정하는 것 |
|---|---|
| 잠든 사이 네이티브가 앞선 만큼이 첫 픽스 반영 뒤 원장에 들어온다 | JS 3050 → 3056으로 6m 전진 후 정산, 크레딧 964m → 총계 정확히 4020m. 스냅샷도 4.02km를 싣는다(저장 경로가 읽는 값) |
| 재생으로 JS가 자력 회복한 만큼은 자동 차감된다 | JS가 3900까지 회복 → 크레딧 120m, 총계는 여전히 4020m |
| JS가 거의 다 따라잡았으면 크레딧을 주지 않는다 | 지터 바닥(80m) 미만은 갭이 아니라 두 누적기의 필터 차이 |
| 크레딧은 잠든 시간의 최대 주행 거리를 못 넘는다 | 60초 잠들고 2km를 주장해도 상한(잠든 시간 × 최대 주행 속도)으로 잘린다 |
| 신호 끊김 문턱보다 짧은 공백은 포획 대상이 아니다 | `MIN_STALE_GAP_MS > MAX_CREDITABLE_FIX_GAP_MS` 를 어서션으로 못 박음 |
| 일시정지된 같은 런에는 정산한다 | 깨어나자마자 종료 = 사고의 실제 흐름 |
| 런이 바뀌면 이관하지 않는다 | `startedAt` 대조 |
| 두 번째 깨어남이 와도 포획은 버려지지 않고 먼저 정산된다 | Face ID·배너의 연속 `active` |
| GPS가 영영 안 오면 타이머가 정산한다 | 실내 종료 |
| 경로 재계산은 신호끊김 직선을 합산하지 않는다 | 5분 공백의 ~1.1km 직선이 빠지고 관측 구간 ~222m만 남는다 |
| 바이너리 판별은 미만·판독불가에서 전부 닫힌다 | 11개 어서션(닫힘 7·열림 4) |
| 정산 뒤 깨어난 시각 이전 픽스는 원장에 못 들어온다 | 수면 꼬리 봉쇄, 런 리셋에 바닥도 사라짐 |

**스위트**: 신선도 수정 시점 backend 536 · client 1405/0 · tsc 0 (`cef20352`), 갭 규칙 이식 시점 client 1409/0 (`35b70a34`), 솔로 확장 마무리 시점 1477 그린 (`040d56d1`).

**변이 테스트에서 나온 값비싼 교훈.** 신선도 수정에 처음 붙인 회귀 테스트 3개는 **수정을 되돌려도 통과했다.** `recordBackgroundTaskStarted()`와 `commitSnapshot()`의 `Date.now()`가 같은 밀리초에 떨어져서 `=== armedAt`이 깨진 구현에서도 성립했기 때문이다 — 변이 생존률 약 95%. 시계를 명시적으로 고정하는 헬퍼(`atClock`)를 넣어 각 스탬프를 정확한 시각에 귀속시킨 뒤, 직접 변이를 실행해 3개 중 2개가 100% 실패하는 것을 확인했다.

## 남은 것 / 배운 것

### 정직한 잔여

- **실기기 확증 미완.** 매치 화면꺼짐 1회, 솔로 화면꺼짐 1회. 코드·테스트·검증은 끝났지만 현장 확증은 안 끝났다. 그리고 이 글의 오진 목록이 보여주듯, **이 프로젝트에서 실기기 확증 전의 결론은 여러 번 틀렸다.**
- **잠든 '동안'의 상대 화면**은 이 OTA 범위 밖이었다. 깨어나는 순간의 스냅백이 정확해졌을 뿐이고, 잠든 중 실시간 병합은 다음 네이티브 빌드(56/46)에서 별도로 들어갔다 — 전송 직전 페이로드의 `distanceKm`을 네이티브 실시간 총거리로 끌어올리되 완주 문턱 아래로 상한을 둔다(`8dea3e50`). 그 상한의 반올림이 42.195km 프리셋에서 문턱에 닿는 문제까지 뒤에 한 번 더 고쳤다(`9c5e4e33`).
- **솔로 런**은 이 시점에 여전히 구멍이었다. 갭 정산은 처음부터 매치를 안 따졌지만 재료인 네이티브 누적기를 켜는 곳이 매치 플러시뿐이었다. 이후 순수 JS 배선으로 확장했고(`efda9516`), **여기서 적대 검증이 설계를 두 번 흔들었다.** 먼저 재파종에 신선도 게이트가 없어 동결된 원장이 정산할 갭 자체를 지우는 경합 두 건을 막았고(`13485ebf`), **그 다음 재검증이 그 게이트가 과했다고 지적했다** — 신호등에 20초 서 있다 화면을 잠근 러너는 "거리가 안 늚 = 동결"로 읽혀 무장 자체가 거부되고, 재무장 경로가 없어 그 세션 전체가 무보호가 된다(고치려던 손실의 부활). 그래서 동결 거부를 **이미 돌고 있는 누적기의 되심기에만** 한정하고, 새 시동은 언제나 허용하도록 되돌렸다(`040d56d1`). *안전 게이트를 넓히는 수정은 그 자체로 손실을 만들 수 있다.*
- **네이티브 시동 성공 여부가 상위에 안 보인다.** Android 포그라운드 서비스 거부가 조용히 삼켜지고, JS는 시동 결과와 무관하게 "돌고 있다"로 기록한다. 다음 네이티브 빌드에서 시동 콜백을 고려 중.
- **수용한 잔여(문서화됨)**: 크레딧이 골을 넘기는 JS 완주는 설계상 합법이다 — 그게 그 사용자가 원래 받았어야 할 완주다. 정지 상태 지터 이관은 80m 바닥과 네이티브 정지 필터로 억제.

### 재사용 가능한 교훈

**1. 이름이 곧 정의고, 정의는 늙는다.** `lastSnapshotAtMs`로 "신선도"를 판정한 코드는 처음 쓰였을 때 아마 맞았다. 나중에 "거부된 픽스도 페이스는 갱신하니까 스냅샷을 커밋하자"가 들어오면서 조용히 뜻이 바뀌었고, **아무도 "이 변수는 무엇을 뜻하는가"를 다시 묻지 않았다.** 결과는 최악의 형태다 — 안전장치가 스스로를 잠그고, 증거까지 지웠다. 판정 신호에는 *무엇을 뜻하는가*를 주석이 아니라 **이름과 테스트**로 박아두는 게 낫다.

**2. "모두가 업데이트하면 켠다"는 조건은 켜지지 않는다.** 최소 버전 강제가 없는 앱에서 함대 조건은 영원한 false다. 게이트는 **기기별 능력 판별**로 걸어야 하고, 판별 불가는 닫힘(fail-closed)이어야 한다. 다만 fail-closed는 실수를 "안전한 침묵"으로 바꾸므로, 래치가 실제로 켜졌는지 관측할 수단이 반드시 같이 있어야 한다.

**3. 판별을 정교하게 만들지 말고, 판별이 필요 없게 만들어라.** 이 글에서 가장 값진 한 수. "OS가 재생을 했는가"를 타임스탬프로 알아맞히는 대신, **뺄셈의 기준점을 '정산 시점의 JS'로 옮겨** 되찾은 몫이 자동 차감되게 했다. 상태를 **추론**하지 말고 **최신 상태를 읽어라.** 상태가 줄고 상수가 줄고, 서로 반대 방향의 버그 두 개가 동시에 사라졌다.

**4. 시간을 비교하는 테스트는 시계를 고정하라.** 안 하면 같은 밀리초에 떨어져 깨진 구현도 통과한다. 이 프로젝트에서 실측된 변이 생존률은 **약 95%**였다. 회귀 테스트를 쓸 때는 항상 **수정을 되돌려서 실제로 실패하는지** 확인한다.

**5. 원장이 둘이면, 어느 쪽이 진실인지 한 곳에 적어라.** 이 사고의 구조적 뿌리는 "iOS가 JS를 잰다"가 아니다 — 그건 OS의 성질이고 바꿀 수 없다. 진짜 뿌리는 **정확한 값을 아는 원장(네이티브)과 저장되는 원장(JS)이 달랐고, 둘을 잇는 길이 업로드 경로에만 나 있었다**는 것이다. 보수적인 설계 결정("업로드에만 병합한다")은 그 자체로는 옳았지만, **그 결정이 사용자가 실제로 잃는 것을 덮는지**는 따로 확인했어야 했다.

**6. 속도 필터는 긴 공백을 못 막는다.** 반직관적이라 두 번 적어둔다 — 블랙아웃이 길수록 그 직선의 암묵 속도는 **낮아지고**, 그래서 속도 기반 방어를 전부 통과한다. 시간 공백에는 **시간 규칙**으로 방어해야 하고, 그 검사는 속도 게이트보다 **앞**에 두어야 한다(뒤에 두면 앵커가 안 옮겨져 남은 러닝 내내 거리가 얼어붙는다).
