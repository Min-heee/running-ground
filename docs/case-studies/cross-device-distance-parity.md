# 같은 코스를 나란히 뛴 두 폰이 서로 다른 거리를 기록한다

**한 줄 요약** — 필터 체인은 이미 플랫폼 공통이었다. 진범은 그 앞단이었다: 안드로이드만 OS 위치 스트림을 "2초 이상 **그리고** 4m 이상 이동했을 때만" 받도록 조여 두어 곡선을 현(弦)으로 잘라 먹으며 체계적으로 짧게 읽었고, 정확도에 비례하는 임계값들이 **벤더별 정확도 추정치 스케일 차이**를 거리 차이로 증폭하고 있었다.

관련 커밋: `56f99e75`(5/29, 선행: 콜드스타트 스파이크) · `bba4e48f`(6/29, 1차 JS/OTA) · `30b6e386`(7/12, 네이티브 필터 이식) · `ffd4fefc`(7/12, 근치: 샘플링 밀도 통일 + 정확도 캡) · `af34db32`(7/31, 후속: 신호 소실 구간 무적립)

---

## 증상

러닝 앱에서 거리는 단순한 표시값이 아니다. 1:1 대결의 승패, 랭킹 포인트, 그라운드 내기 정산이 전부 이 숫자 위에 얹혀 있다. 두 기기가 다른 숫자를 내면 그건 표시 버그가 아니라 **판정 불공정**이다.

재현 조건은 단순했다. 한 사람이 iPhone과 Galaxy를 동시에 들고 같은 코스를 한 번 뛰고, 두 폰 모두 앱으로 기록한 뒤, 저장된 거리를 비교한다.

관측된 것:

| 증상 | 내용 | 출처 |
|---|---|---|
| 시작 스파이크 | iPhone이 출발 직후 약 +0.3km를 먼저 얹고 시작 | `bba4e48f` |
| 안드로이드 과다계상 | 지터가 그대로 거리로 적립되던 구간 | `bba4e48f` |
| 안드로이드 과소계상 | 위 두 개를 고친 뒤 남은, 곡선 구간에서의 **체계적** 짧은 기록 | `ffd4fefc` |

마지막 항목이 이 글의 주제다. "가끔 튄다"가 아니라 **한 방향으로 일관되게** 짧았다. 랜덤 노이즈였다면 코스가 길수록 상쇄되어야 하는데 그렇지 않았다는 점이, 나중에 보니 결정적인 단서였다.

같은 두 폰 측정 세션에서 고도(Galaxy 410m vs iPhone 56m, 평지 5km)와 케이던스(3spm vs 154spm) 문제도 같이 나왔고, 그 둘은 별건으로 `cbc4c706`에서 근치했다. 이 글에서는 거리만 다룬다.

## 처음 의심한 것 (그리고 왜 틀렸나)

### 가설 1 — "JS 필터 체인이 플랫폼마다 다르겠지"

가장 자연스러운 가설이었다. 거리 누적기에는 게이트가 많다. 정확도 하드 리젝, 최소 시간 델타, 순간이동 게이트 2종, 정지/저정확도 노이즈 억제, 정확도 비례 거리 게이트, 콜드스타트 워밍업 폐기, 측면 지터 접기. 이 중 하나라도 `Platform.OS` 분기를 갖고 있으면 바로 설명이 된다.

반증은 grep 한 번이었다. **그리고 그 출력에는 진범이 이미 들어 있었다.**

```
$ git grep -n "Platform.OS" -- src/features/runs/tracking/background/
index.ts:70:      if (Platform.OS !== 'android') {                 // 알림 채널
locationTask.ts:19:  const isIOS = Platform.OS === 'ios';          // ← 이것
locationTask.ts:47:    ...(Platform.OS === 'android'                // 포그라운드 서비스 알림 문구
locationTask.ts:78:    flushBackgroundMatchProgressSync({ platform: Platform.OS })  // 진단 태그
locationTask.ts:82:if (Platform.OS !== 'web') {                    // 태스크 정의 가드
subscriptions.ts:18:  platform: Platform.OS,                        // 진단 태그
```

내가 찾던 것은 "수락/거절을 플랫폼마다 다르게 하는 코드"였고, 그런 코드는 정말 없었다. `routeAccumulator.ts`의 `appendTrackedLocation`은 두 플랫폼에서 바이트 동일하다. 같은 점열이 들어오면 같은 거리가 나온다.

문제는 19번 줄이 12줄 아래에서 이렇게 쓰이고 있었다는 것이다.

```ts
// locationTask.ts:31 (수정 전)
distanceInterval: isIOS ? 0 : 4,
```

이건 필터가 아니라 **수집 설정**이다. 그래서 나는 이 줄을 "필터 분기 없음"의 반례로 세지 않고 눈으로 넘겼다. 가설 1은 좁은 의미에서 정확히 죽었고, 정확히 그 좁힘 때문에 진범이 6주를 더 살았다.

### 가설 2 — "게이트 상수가 느슨해서 노이즈가 새는 쪽이 이긴다"

이건 **부분적으로 참**이었고, `bba4e48f`에서 고쳤다.

1. **콜드스타트 시드 = 0.** 워밍업 클러스터가 잡히기 전의 배회 경로를 t0 거리로 은행에 넣고 있었다. +0.3km 시작 스파이크의 주된 몫이 이것이었다.
2. **게이트 조이기.** `MAX_TRACKING_ACCURACY 60 → 40m`, 최소 이동/거리 게이트 베이스 `2.5 → 3.0m`, 콜드스타트 정확도 문턱 `30 → 20m`.
3. **병합 규칙 교체.** 화면 꺼짐 대비 네이티브 누적기와 JS 누적기를 `max(js, native)`로 합치고 있었는데, 이건 **더 시끄러운 쪽이 항상 이기고 그 잉여를 영구히 고정**하는 구조였다.

```ts
// src/features/runs/tracking/background/distanceAccumulatorController.ts
//   mergedDistanceKm =
//     (!nativeMergeEnabled || !nativeAvailable) ? jsDistanceKm
//   : jsIsFresh                                 ? jsDistanceKm      // 신선 → JS 그대로
//   : /* JS stale (screen off) */                 max(lastFreshJsKm, nativeKm)
```

시작 스파이크는 기대치 기준 0.3km → 30m 미만으로 잡혔다. 그런데 **두 폰의 차이는 남았다.**

### 가설 3 — "화면 꺼짐 네이티브 누적기가 JS와 다르다"

이것도 **참**이었다. 안드로이드 Kotlin 포그라운드 서비스와 iOS Swift 모듈이 각자 들고 있던 `consume()`은 JS 체인의 게이트 중 상당수를 갖고 있지 않았다. 게다가 안드로이드에는 **fail-open 버그**가 있었다: 정확도 값이 없는 fix가 `0.0`(최상)으로 읽혀 가장 좁은 게이트를 그대로 통과했다.

`30b6e386`에서 JS 체인 전체를 두 네이티브 누적기에 이식했다.

- JS와 동일한 순서: 정확도 → 나이 창 → 콜드스타트 워밍업 → 최소 시간 델타 → 순간이동 게이트 2종 → 정지/저정확도 노이즈 → 정확도 비례 거리 게이트 → 적립
- JS와 동일한 **이중 앵커**: 세그먼트 필터는 마지막 *append* 지점 기준, 거리 게이트와 적립 총량은 마지막 *counted* 지점 기준
- 정확도 없는 fix는 fail-**closed**로 전환

이 과정에서 더 고약한 걸 하나 발견했다. 안드로이드 네이티브 모듈이 서비스 인텐트로 옵션을 넘길 때 **원래의 6개 키만 통과시키고 있어서**, `bba4e48f` 이후 JS가 계속 내려보내던 새 상수들이 한 번도 적용된 적이 없었다. "모르는 키는 무시한다"로 OTA-safe하게 설계한 와이어 포맷의 반대편에서, 정작 아는 키가 조용히 누락되고 있었던 것이다.

빌드 44에 실려 나갔다. 다만 정직하게 적으면 — **이 배치와 다음 배치 사이에 실주행 재측정은 없었다.** 두 커밋은 같은 날 네 시간 간격이다(7/12 17:34 → 21:56). 다음 단계로 밀어붙인 근거는 새 측정이 아니라, 앞선 배치들이 소진되고도 남아 있던 6월 말의 관측과 아래의 논리였다.

### 오진의 기록 — 내가 문서로 못 박아 둔 잘못된 결론

부끄러운 부분이라 그대로 남긴다. 2026-07-05 설계 문서([`docs/metric-parity-design-2026-07-05.md`](../../docs/metric-parity-design-2026-07-05.md))에서 나는 거리 문제를 이렇게 종결시켰다.

> ③ DISTANCE / PACE — **within GPS tolerance, NO CHANGE**
> (…) `locationTask.ts:31`의 배경 샘플링 설정이 플랫폼별로 다른 것은 **의도된 설계**이며 화면 꺼짐 동기화 생명줄의 일부다. **건드리면 보호 중인 시스템이 약해진다** — 명시적으로 범위 밖.

즉 나는 **진범의 파일과 줄 번호까지 문서에 적어 놓고, 그것을 "만지면 안 되는 것"으로 분류해서 용의선상에서 제외했다.** 근거도 그럴듯했다. iOS의 `distanceInterval: 0`은 화면 꺼짐 플러시를 살려두려고 일부러 넣은 것이었고, 안드로이드의 `4m`는 당시 JS 스레드 포화 이슈(#195/#201)를 악화시키지 않으려고 보수적으로 둔 것이었다. 둘 다 진짜 이유가 있는 설정이었다.

문제는 **"의도된 설정"과 "무해한 설정"은 다른 말**이라는 것이다. 의도를 알고 있다는 사실이, 그 의도가 다른 지표에 부작용이 없다는 증명이 되어 주지 않는다.

### 전환점

세 개의 사실이 남았다.

1. 수락/거절 코드는 두 플랫폼에서 동일하다. (가설 1)
2. 상수를 조여도, 네이티브까지 같은 체인으로 맞춰도 차이가 남는다. (가설 2·3 소진)
3. 차이의 부호가 일정하다 — 안드로이드가 **항상** 짧다.

같은 함수에 넣었는데 다른 답이 나오고, 그 다름에 방향이 있다면, 남은 곳은 하나뿐이다. **입력이 다르다.** 필터를 보는 걸 멈추고 필터가 무엇을 받고 있는지를 봤다. 두 번 지나쳤던 그 줄이 거기 있었다.

## 진짜 근본 원인

### 뿌리 1 — 입력 샘플링 밀도의 비대칭

수정 전, 두 스트림의 옵션은 이랬다.

| 스트림 | iOS | Android |
|---|---|---|
| 백그라운드 태스크 (`locationTask.ts`) | `distanceInterval: 0` (모든 fix) | `distanceInterval: 4`, `timeInterval: 2000` |
| 포그라운드 워치 (`foregroundSubscription.ts`) | `distanceInterval: 4`, `timeInterval: 2000` | `distanceInterval: 4`, `timeInterval: 2000` |

여기서 구조적으로 중요한 사실 하나: **두 스트림은 러닝 중 동시에 살아 있고, 둘 다 같은 `appendTrackedLocation`을 먹인다**(`locationTaskPolicy.ts` — 포그라운드 워치는 인앱 GPS 신뢰성 때문에, 백그라운드 태스크는 화면 꺼짐 때문에 둘 다 상시 무장). 따라서 누적기가 실제로 보는 입력은 두 스트림의 **합집합**이다.

- iOS: bg 스트림이 `0m`로 모든 fix를 흘려보내므로 합집합은 사실상 **~1Hz 전량**.
- Android: 두 스트림 모두 `2초 AND 4m` 이므로 합집합도 **0.5Hz + 4m 변위 사전 게이트**.

추가로 `timeInterval`은 expo-location 문서상 **Android 전용 옵션**이다. iOS에서는 값이 무엇이든 무시되고, 사실상 안드로이드 전용 스로틀로만 작동하고 있었다.

결과적으로 두 폰은 같은 길을 **다른 해상도로 샘플링한 다른 폴리라인**을 적분하고 있었다.

### 왜 하필 "짧게" 나오는가 — 현(弦) 절단

곡선을 점열로 근사하면 항상 실제 호(弧)보다 짧다. 반지름 R의 원호를 현 길이 c로 샘플링할 때 폴리라인 길이는 실제의 `sin(θ/2)/(θ/2)` 배(θ = c/R)다. **아래는 측정치가 아니라 순수 기하 계산이다.**

| 곡률 | 현 ~3m (1Hz, 3m/s) | 현 ~6m (0.5Hz, 3m/s) | 차이 |
|---|---|---|---|
| 직선 | 0% | 0% | 0 |
| 완만한 굽이 (R=25m) | −0.06% | −0.24% | 0.18%p |
| 좁은 공원 벤드 (R=8m) | −0.59% | −2.33% | 1.74%p |

여기에 **4m 변위 사전 게이트**가 얹히면 효과는 이 기하학적 하한보다 커진다. 느린 속도로 좁게 도는 구간에서는 **실제 이동 경로는 7~8m인데 시작점 대비 순변위는 4m 미만**인 상황이 흔하다. 그런 fix는 OS 단에서 아예 배달되지 않으므로, JS 필터 체인은 그 구간이 존재했다는 사실조차 알 수 없다. 필터가 아무리 정교해도 **오지 않은 점은 복원할 수 없다.**

코스가 직선이면 두 폰이 일치하고, 굽이가 많으면 벌어지고, 부호는 항상 안드로이드가 짧다 — 관측된 증상의 세 가지 성질이 모두 이 하나로 설명됐다.

### 이 인과를 얼마나 믿을 수 있나

**지지하는 것**: 수락/거절 코드가 동일하다는 것은 코드로 확인됐다. 상수 조이기와 네이티브 정렬 두 배치로도 차이가 닫히지 않았다. 부호가 일정하다. 기하 모델은 부호뿐 아니라 **곡률 의존성**까지 예측하고, 그것이 관측과 맞는다. 수정은 정확히 그 예측된 축(샘플링 밀도)만 건드린다.

**지지하지 않는 것**: 위 표는 **하한**이다. 6월 말 관측치인 1~3% 괴리 전부를 이 표만으로 설명할 수는 없고, 4m 사전 게이트의 추가 기여분은 계량하지 않았다. 무엇보다 **수정 후 두 폰 A/B가 없다.** 따라서 정확한 진술은 "이것이 측정으로 확증된 유일한 원인"이 아니라 **"남은 사실 셋을 동시에 설명하는 유일한 후보이고, 다른 후보들은 코드로 배제됐다"**이다. 이 정도가 지금 가진 증거의 한계다.

### 뿌리 2 — 정확도 추정치 × 정확도 비례 임계값 = 증폭기

두 번째 뿌리는 더 미묘하다. 필터 체인의 임계값 여러 개가 정확도에 비례한다.

```ts
// 수정 전: src/features/runs/tracking/background/locationDistance.ts
export function resolveDistanceGateMeters(worstAccuracyM: number) {
  return DISTANCE_GATE_BASE_METERS + Math.max(0, worstAccuracyM) * DISTANCE_GATE_ACCURACY_SCALE;
}
```

의도 자체는 옳다. 부정확한 fix일수록 더 크게 움직여야 "진짜 이동"으로 인정해야 한다.

문제는 `worstAccuracyM`이 **물리량이 아니라 벤더의 추정치**라는 점이다. 같은 품질의 fix에 대해 싱글밴드 칩은 10~20m를, 멀티밴드 칩은 3~8m를 보고한다. 둘 다 명목상 1σ지만 추정기의 캘리브레이션이 다르다.

```
Galaxy: 정확도 추정 20m 보고 → 거리 게이트 3.0 + 20×0.15 = 6.0m
iPhone: 정확도 추정  6m 보고 → 거리 게이트 3.0 +  6×0.15 = 3.9m
```

같은 실제 품질의 fix인데 한쪽만 게이트가 넓어진다. 즉 **정확도 비례 임계값은 "칩이 자기 오차를 얼마나 비관적으로 보고하는가"를 "얼마나 짧게 기록되는가"로 번역하는 증폭기**로 작동하고 있었다. 이미 밀도가 낮아 짧게 읽는 기기에서, 게이트까지 더 넓어져 굵은 현만 적립됐다.

## 해결

### 1) 샘플링을 플랫폼 동일로 — 안드로이드를 **올려서** 맞춘다

```ts
// src/features/runs/tracking/background/locationTask.ts (수정 후)
timeInterval: 1000,
distanceInterval: 0,
```

포그라운드 워치도 같은 값으로 바꿨다. 합집합이 입력이므로 **한쪽만 풀면 의미가 없다** — 포그라운드가 4m 사전 게이트를 유지하면 bg에서 없앤 변위 필터링이 그대로 재유입된다.

**왜 iOS를 안드로이드에 맞춰 내리지 않았나.** iOS의 `distanceInterval: 0`은 화면 꺼짐 상태에서 매치 진행률 플러시를 깨우는 생존 트리거다. 이걸 조이면 이미 해결한 백그라운드 동기화 문제가 되살아난다. 아래로 맞추는 통일은 다른 시스템을 부순다.

**왜 플랫폼별 보정계수를 곱하지 않았나.** 짧게 나오는 쪽에 계수를 곱하는 방법은 원인을 고치지 않고 증상만 가린다. 코스 곡률에 따라 필요한 계수가 달라지므로(위 표: 직선 0%, 좁은 벤드 1.74%p) 상수 하나로는 어디서든 틀리고, 무엇보다 **거리가 승패를 정하는 앱에서 특정 기기의 기록에 임의 계수를 곱하는 것**은 정당화하기 어렵다.

### 2) 진짜 샘플러는 OS가 아니라 공용 게이트다

fix 수를 늘려도 부하가 폭증하지 않는 이유는, 비싼 단계에 닿기 전 — 정확도 하드 리젝과 콜드스타트 처리 직후 — 에 900ms 최소 시간 델타 게이트가 있기 때문이다.

```ts
if (timeDelta < MIN_LOCATION_TIME_DELTA_MS) {   // 900ms
  commitSnapshot({ ...snapshotState, currentPace: /* 페이스만 갱신 */ });
  return;
}
```

즉 "얼마나 자주 셀 것인가"의 결정권을 **OS의 벤더별 사전 게이트에서 우리 코드의 단일 상수로 회수**한 것이 이 수정의 본질이다.

성능 우려에 대한 근거: 당시 안드로이드 JS 스레드 포화 이슈는 **렌더 기인**이었다(별도 조사에서 1Hz 타이머의 전체 트리 리렌더로 특정, `b32cbcde`에서 quiesce). 살아남은 fix가 지불하는 비용은 경로 append + 페이스 윈도우 + 고도 패스로 유계이고, 이는 iOS가 이미 같은 1Hz/0m 설정으로 출하 중이던 비용 프로파일과 동일하다.

### 3) 정확도 스케일 캡 — 스케일링에만, 판정에는 아니게

```ts
// src/features/runs/tracking/background/locationDistance.ts
export const ACCURACY_SCALE_CAP_METERS = 15;

// 임계값을 '스케일'하는 자리에만 쓴다. 하드 리젝 비교에는 절대 쓰지 않는다.
export function capAccuracyForThresholdScaling(accuracyM: number) {
  return Math.min(Math.max(0, accuracyM), ACCURACY_SCALE_CAP_METERS);
}
```

적용 원칙을 세 갈래로 명확히 나눴다.

| 용도 | 캡 적용 | 이유 |
|---|---|---|
| 임계값을 **스케일**하는 항 (거리 게이트, 동적 최소이동, 저정확도 반경, 지터 접기) | ✅ 캡 | 벤더 추정치 차이가 게이트 폭 차이로 번역되는 것을 차단 |
| **하드 리젝** (`accuracyM > MAX_TRACKING_ACCURACY_METERS` → fix 폐기) | ❌ raw | 진짜로 형편없는 fix는 그대로 버려야 한다 |
| **분류** 비교 (`worstAccuracyM >= POOR_ACCURACY_METERS`) | ❌ raw | 이건 "나쁜 fix인가"를 판정하는 것이지 임계값을 늘리는 것이 아니다 |

캡의 효과는 상한이 생긴다는 것이다. 거리 게이트는 정확도가 아무리 비관적으로 보고돼도 `3.0 + 15×0.15 = 5.25m`를 넘지 않는다. 동적 최소이동은 `15×0.1 = 1.5m`가 되어 3.0m 베이스 바닥을 절대 못 넘으므로 두 기기에서 완전히 동일해진다.

### 4) 정지 억제 반경만은 캡에서 **제외** — 적대 검증이 되돌린 부분

처음엔 정확도 비례 임계값 전부에 캡을 걸었다. 적대 검증에서 회귀가 나왔다.

```ts
// STATIONARY radius deliberately EXEMPT from the accuracy cap: ...
const stationaryNoiseRadiusMeters = Math.max(4, Math.min(12, worstAccuracyM * 0.35));
```

논리는 이렇다. 정지 억제 반경은 **이미 정지로 분류된** 세그먼트만 버린다. 따라서 아무리 커져도 진짜 러닝을 삼킬 수 없다 — 캡을 걸어 얻을 공정성 이득이 없다. 반대로 4m OS 사전 게이트를 없앤 지금, 시끄러운 기기는 신호등 앞에 서 있는 동안 멀티패스 드리프트를 1Hz 전량으로 받는다. 여기서 반경을 좁히면 **가만히 서 있는데 거리가 늘어난다.** 캡의 목적(추정치 차이가 게이트를 넓히는 것 차단)이 여기서는 성립하지 않으므로 예외로 뒀다.

### 5) 곁다리 하나 — 보행계 pause/resume 오프셋

같은 배치에서 `usePedometerTracking.ts`의 버그를 하나 고쳤다. 재구독 시 `watchStepCount`가 0부터 다시 세는데 오프셋이 기존 누적을 흡수하지 않아, 일시정지/재개 한 번에 전체 걸음 수가 아래로 스냅됐다.

```ts
// 재구독 직전에 이미 센 걸 오프셋이 흡수한다
pedometerStepOffsetRef.current = totalStepsRef.current;
```

거리 자체와는 무관하지만 넣은 이유가 있다. 같은 배치에 서버 측 자동 부정행위 판정이 함께 나가고 있었고, 케이던스가 인위적으로 무너진 실제 러닝이 그 판정에 오탐으로 걸릴 수 있었다. 자동 판정을 켤 때는 그 입력을 오염시키는 버그를 같은 배치에서 같이 닫아야 한다.

## 검증

### 유닛 테스트로 못 박은 것

새로 만든 `locationDistance.test.ts`가 캡의 경계를 전부 고정한다.

```ts
// 정확도 20 fix는 정확히 정확도 15 fix와 같은 게이트를 받는다
assert.equal(resolveDistanceGateMeters(20), 5.25);
assert.equal(resolveDistanceGateMeters(12), 4.8);          // 캡 아래는 그대로 비례
assert.equal(resolveDistanceGateMeters(MAX_TRACKING_ACCURACY_METERS), 5.25);
```

- **동적 최소이동**: 정확도 45에서도 3.0m 베이스 바닥 = 두 기기 동일
- **정지 반경 예외**: 정확도 40에서 반경 12m가 유지되고(6m/0.8m/s 세그먼트 → 버림), 13m는 통과, 러닝 속도(3.2m/s)에서는 애초에 분기가 안 탐
- **저정확도 분기**: 분류는 raw로 남되 반경만 캡(3.5m 버림 / 4m 통과)
- **하드 리젝 불변**: 정확도 41m fix는 여전히 즉시 폐기

누적기 레벨에서는 **캡 적용 여부를 판별하는** 테스트를 넣었다. 정확도 20에서 5.6m 세그먼트는 구(舊) 게이트 6.0m에서는 조용히 버려지고, 신(新) 캡 게이트 5.25m에서는 적립된다 — 정확히 그 사이 값이라 두 동작을 구분한다(`route.length === 4`, 적립량 5.2~6.0m).

### 적대 검증이 잡아 되돌린 과소계상 2건

`bba4e48f` 배치에서 출시 전 적대 검증이 **내가 넣으려던 값 두 개를 반려**했다. 둘 다 "노이즈를 더 잡자"는 방향이었고, 둘 다 실제로는 진짜 거리를 깎았다.

| 되돌린 것 | 무엇이 깨졌나 | 최종 채택값 |
|---|---|---|
| 콜드스타트 클러스터 반경 30m → **15m** | 약 3.75m/s보다 빠르게 출발하는 러너는 워밍업 클러스터가 **형성 자체가 안 됨** → 앵커가 안 잡히고 **런 전체가 0km** | **30m 유지** (스파이크를 죽인 건 반경이 아니라 시드=0이었다) |
| 거리 게이트/최소이동 바닥 2.5m → **5.0m** | 공원 굽이길에서 **3~18% 과소계상** | **3.0m** |

두 번째는 특히 뼈아프다. 5.0m 바닥은 정확히 이 글의 진범(현 절단)을 소프트웨어로 재현하는 값이었다. 즉 나는 "안드로이드가 짧게 나온다"를 고치려던 배치에서, 하마터면 **두 기기 모두에 같은 병을 옮길 뻔했다.**

`ffd4fefc` 배치에서는 적대 검증이 위의 정지 억제 반경 예외를 잡아냈다.

### 스위트

- `bba4e48f`: tsc 0 / eslint 0 / 922 테스트, 합성 5km 직선 코스가 여전히 1% 이내
- `cbc4c706`(자매 배치): +6 테스트, 스위트 1060 통과, 2000개 노이즈 경로 퍼징, 거리는 바이트 동일

### 실측 — 그리고 이 실측을 어떻게 읽어야 하는가

정직하게 쓴다. **`ffd4fefc` 이후의 두 폰 재측정 기록은 남아 있지 않다.** 내가 갖고 있는 실측 대조는 한 대(iPhone)로 서드파티와 비교한 것뿐이고, 아래는 저장소에 로그로 남은 데이터가 아니라 현장 기록이다.

2026-08-01, 10km 러닝(호수공원 코스, iPhone):

| 앱 | 거리 | 페이스 |
|---|---|---|
| 우리 | 10km | 6:29 |
| Strava | 10.00km | 6:28 |
| Nike | 9.47km | — |

전 구간 Strava와 0.5% 이내, 최종값 동일. Nike는 약 5% 낮게 나왔다.

여기서 멈추면 안 된다. **3주 전인 7/31, 같은 방식의 대조에서 우리가 3.8km, Nike가 3.0km를 찍었다.** 그때는 Nike가 보수적이었던 게 아니라 **우리가 틀렸다.** 고가도로 밑에서 GPS가 분 단위로 끊겼다 수백 m 떨어진 곳에서 재획득되면, 그 직선의 암묵 속도(거리÷끊긴 시간)가 달리기 속도만큼 낮아 속도 기반 순간이동 필터를 전부 통과하고 직선이 통째로 적립됐다. `af34db32`에서 "유효 픽스 없이 30초를 넘긴 구간의 직선은 적립하지 않는다"로 막았다.

그래서 위 8/1 표에는 단서가 둘 붙는다.

1. 이 표는 **7/12 배치의 성적표가 아니라 `af34db32`까지 포함한 파이프라인의 성적표**다.
2. "Nike가 보수적인 것이지 우리가 부풀린 게 아니다"라는 해석은, 3주 전이었다면 정확히 틀렸을 해석이다. 이번에 그 해석이 성립하는 근거는 Nike보다 우리를 믿어서가 아니라 **같은 시점 Strava가 우리와 0.5% 이내로 일치했기 때문**이다. 대조군이 하나뿐이면 이 해석은 하면 안 된다.

이 데이터가 증명하는 것: **절대 정확도는 업계 기준선 안에 있다.** 증명하지 못하는 것: **두 기기 간 잔차가 실제로 얼마나 줄었는지.** 후자는 여전히 미검증이다.

## 남은 것 / 배운 것

### 남은 것 (정직한 공시)

**1. 칩 물리 차이는 못 없앤다 — 다만 그 크기는 추정치다.**
멀티밴드(L1/L5) 수신기와 싱글밴드 수신기는 도심 멀티패스 환경에서 애초에 다른 품질의 fix를 만든다. 이건 필터의 문제가 아니라 안테나와 주파수의 문제다. 굽이가 많은 코스에서 두 기기 간 **0.5~1% 잔차가 남을 것으로 본다** — 다만 이 수치는 측정된 값이 아니라 커밋 시점의 내 예상치이고, 위의 미검증 항목이 닫히기 전까지는 그 이상으로 주장하지 않는다.

**2. 네이티브 누적기에는 아직 캡이 없다.**
JS 체인은 15m 캡을 쓰지만, 화면 꺼짐 구간을 메우는 네이티브 누적기는 와이어 상수를 그대로 받아 **캡 없이** 게이트를 돌린다. 이 TODO는 지금도 코드에 서 있다.

```ts
// TODO(next native build): ... 네이티브에 미러링하려면 새 옵셔널 와이어 키(accuracyCapMeters)가
// 필요하고 그건 다음 바이너리가 읽어야 한다. 지금 키를 추가하지 마라: 현재 네이티브는 모르는 키를
// 무시하므로 무의미하고, 반쪽만 배선된 키는 혼란만 부른다 — 네이티브가 읽는 법을 배우는 그 변경에서
// 같이 추가하라.
```

**inert한 상태로 존재하는 설정 키는, 나중에 그 키가 이미 동작 중이라고 착각하게 만든다.** 실제로 이 프로젝트에서 안드로이드 인텐트가 새 옵션 키를 조용히 흘려 "보내고 있으니 적용되고 있겠지"라고 몇 주를 믿었던 전례가 있다.

**3. 두 폰 재측정.** 위에 쓴 대로 미완이다. 이게 닫히기 전까지 이 글의 결론은 "가장 잘 설명하는 가설"이지 "확증된 인과"가 아니다.

### 배운 것

**필터가 같은데 답이 다르면, 입력을 봐라.**
같은 순수 함수에 넣었는데 다른 결과가 나온다면 가능성은 둘뿐이다 — 함수가 순수하지 않거나, 입력이 다르거나. 그리고 부호가 일정한 오차는 랜덤이 아니다. 차이가 항상 한 방향이면 그건 노이즈가 아니라 체계적 편향이고, 체계적 편향에는 언제나 구조적 원인이 있다. 이 단서를 더 일찍 진지하게 받아들였다면 "GPS 허용오차"로 종결시키지 않았을 것이다.

**"의도된 설정"은 "무해한 설정"이 아니다.**
나는 진범을 grep 출력에서 한 번, 7/5 설계 문서에서 파일명과 줄 번호까지 적어가며 또 한 번 봤다. 두 번 다 "이건 수집 설정이지 필터가 아니야", "이건 일부러 그런 거야"로 분류하고 넘겼다. 어떤 설정이 왜 그 값인지 **알고 있다는 사실이, 그 값이 다른 지표를 오염시키지 않는다는 증명이 되어주지 않는다.** "일부러 그런 것"은 조사를 멈출 이유가 아니라, 고칠 때의 제약 조건일 뿐이다.

**추정치를 임계값에 곱할 때는 상한이 필요하다.**
`threshold = base + k × accuracy` 같은 식은 `accuracy`가 물리량일 때만 안전하다. 그것이 **벤더가 자기 오차를 얼마나 비관적으로 보고하는지**라면, 그 식은 보고 스타일의 차이를 측정값의 차이로 번역하는 증폭기가 된다. 캡을 걸되 — **스케일링하는 항에만 걸고, 하드 리젝과 분류 비교에는 절대 걸지 마라.**

**노이즈를 더 잡는 방향의 변경은 "진짜를 얼마나 깎는가"로 반대 심문해야 한다.**
적대 검증이 반려한 두 값은 모두 "더 엄격하게" 방향이었고, 각각 빠른 출발 러너의 런 전체를 0km로 만들거나 굽이길을 3~18% 깎았다. 노이즈 억제 변경의 리뷰 질문은 "이게 노이즈를 잡나?"가 아니라 **"이게 어떤 실제 러너를 손해 보게 하나?"** 여야 한다.
