## 1. 한 줄 정의와 문제

**서로 다른 장소에 있는 두 대 이상의 폰이 같은 시각에 출발해 같은 거리를 달리고, 그 승패를 서버가 판정하는 앱입니다.**

혼자 뛰는 앱이라면 거리가 1% 짧게 찍혀도 개인 기록이 아쉬울 뿐입니다. 승패가 붙는 순간 같은 1%가 **판정 불공정**이 됩니다. 실제로 겪은 형태입니다.

- 두 폰의 시계가 수백 ms 어긋나면 한쪽은 이미 출발했는데 다른 쪽은 아직 "3"을 셉니다. 출발선이 다른 경기입니다.
- 같은 코스를 나란히 뛴 갤럭시와 아이폰이 다른 거리를 기록했습니다. 곡선 구간에서 안드로이드가 **한 방향으로 일관되게** 짧게 읽었습니다.
- 한 사용자가 화면을 끄고 달렸습니다(2026-08-17). 같은 코스를 전보다 빨리 뛰었는데 목표 5km에 못 미친 기록으로 끝났습니다. iOS는 화면이 꺼지면 JS 스레드를 재우고, 거리 계산이 멈춥니다.
- 사람의 달리기로 설명되지 않는 속도(시속 30km대)로 이동한 차량 기록이 **'오늘의 랭킹' 1위에 올랐습니다.** 저장 시점의 속도 규칙이 `vehicle` 판정을 내렸는데도 표시면이 그 판정을 읽지 않고 있었습니다([`competitiveRuns.mjs`](../backend/src/lib/competitiveRuns.mjs) · [`cadenceWatchdogModel.ts`](../src/features/runs/integrity/cadenceWatchdogModel.ts) 머리 주석).

진짜 문제는 측정 정확도가 아닙니다. **서로 다른 기기·플랫폼·전원 상태에서 나온 숫자를 하나의 판정으로 묶는 일**입니다.

## 2. 목표와 비목표

**목표**

1. 두 폰이 같은 순간에 0을 봅니다.
2. 두 플랫폼이 같은 모양의 입력으로 거리를 누적합니다.
3. 화면을 꺼도 기록이 짧아지지 않고, 이중 적립도 되지 않습니다.
4. 사람이 달린 것이 아닌 기록을 경쟁 지표에서 뺍니다. 단 **억울한 실격 0건**이 정확한 적발보다 우선입니다.
5. 판정 코드에 버그가 있어도 기록은 사라지지 않습니다.

**비목표 — 이번 범위에서 하지 않기로 한 것**

| 하지 않은 것 | 이유 |
| --- | --- |
| 플랫폼별 거리 보정계수 | 증상만 가림. 필요한 계수가 코스 곡률에 따라 달라지고(직선 0%, 좁은 벤드 1.74%p), 거리가 승패를 정하는 앱에서 특정 기기에 임의 계수를 곱하는 건 정당화하기 어려움 |
| 케이던스(분당 걸음)만으로 유죄 | 안드로이드는 화면이 꺼지면 걸음 센서를 해제함(`expo-sensors`의 `onHostPause`). 케이던스가 통째로 비는 정직한 러닝이 관측됨 |
| 부정 판정으로 **상대의** LP(랭크 점수)나 매치 승패를 뒤집기 | 되돌릴 때 영향을 받는 범위가 넓음(상대 보상 회수, 알림 재발송) |
| GPS 궤적을 재검증하는 리플레이 안티치트 | 저장 시점 규칙 + 러닝 중 워치독으로 먼저 막고 백로그로 남김 |
| 절대 거리 정확도 자체 개선 | 목표는 **두 기기 사이의 일치**. 둘 다 2% 짧아도 경기는 공정함 |

## 3. 사용자와 시나리오

사용자는 **혼자 뛰면 심심해서 안 뛰는 사람**입니다.

**A — 1:1 대결(서로 다른 장소)**

1. 거리(추천 3·5·7·10·15·21.1·42.195km)와 시작 시각을 골라 슬롯을 예약합니다.
2. 서버가 평균 페이스 ±15초/km 안의 상대를 붙이고, 두 폰에 `slotStartAt`(절대 서버 시각)과 `serverNow`를 내려줍니다.
3. 각 폰은 그때부터 모든 API 응답으로 서버 시계 오프셋을 추정합니다. 출발 30초 전 오버레이가 뜨고, 20초 전에 아레나 화면이 오버레이 **아래에** 먼저 마운트됩니다.
4. 0초에 동시 출발해 2.5초마다 진행률을 올리고, 상대의 거리·페이스·순위를 받습니다.
5. 목표를 넘기면 완주 푸시를 보냅니다. 서버가 **측정된 완주 경과시간**으로 순위를 정해 판정을 봉인(= 더는 뒤집히지 않게 확정)하고 LP를 적용하며, 양쪽이 같은 결과 화면을 봅니다.

**B — 화면을 끄고 달리는 사람.** 배터리 때문에 출발 직후 화면을 끄는 사용자가 많습니다. JS 거리 계산은 멈추지만 GPS는 계속 옵니다. 앱은 네이티브(Swift/Kotlin) 누적기를 함께 돌려 그 구간을 재고, 화면을 켜는 순간 **네이티브가 앞선 만큼만** 얹습니다. 사용자에게는 "화면 켰더니 거리가 맞게 따라와 있다"가 전부이고, 그게 성공 조건입니다.

랭킹·크루 리그·친구·기록 등 나머지 기능은 같은 코드베이스에 있습니다([`architecture.md`](architecture.md), [README](../README.md)).

## 5. 규칙·판정 설계 — 숫자와 경계값

공개 저장소이므로 상수를 그대로 적습니다. **콜드스타트**는 앱을 막 켠 직후의 불안정한 구간, **픽스**는 GPS 측정값 한 건을 가리킵니다.

### 시각 합의

`offsetMs = serverNow + rtt/2 − 응답수신시각`.

| 경계값 | 처리·이유 |
| --- | --- |
| RTT 샘플 상한 3,000ms · 버퍼 8개 · 신선도 12,000ms | 오래되거나 왕복이 긴 샘플은 오프셋 추정에서 제외 |
| 적용 문턱 100ms · 지터 허용 150ms · 한 번에 움직이는 최대 폭 400ms | 늦게 온 스냅샷이 화면의 숫자를 점프시키지 못하게 함 |
| `clockReady` = 신선 샘플 2개가 250ms 이내로 일치 | 성립 전에는 카운트다운 잠금이 목표 시각을 동결하지 못함 |
| 콜드스타트 스냅은 RTT 500ms 이하를 '좋은 샘플'로 인정 | 앱을 막 켠 직후에도 한 번은 시계를 맞춰야 함 |
| 진입: 오버레이 30초 / 아레나 20초 / 예약방 핸드오프 25초 | 25는 반드시 20과 30 **사이** |
| 방장 시작: 누름 + 로딩 5초 + 보이는 10초(상한 14초) | 상한의 출처는 4절의 2026-07-03 실기기 측정 |

**애매한 경우** — 편도 지연이 비대칭이라 샘플마다 ±RTT/2의 불확실성이 있습니다. 그래서 **가장 최근 샘플 대신 RTT가 가장 작은 샘플**을 신뢰합니다.

### 거리 측정

| 경계값 | 처리·이유 |
| --- | --- |
| 양 플랫폼 `timeInterval 1000` / `distanceInterval 0` | 입력의 모양 자체를 같게 맞춤 |
| 최소 시간 델타 900ms · 픽스 나이 상한 15초 · 미래 픽스 3초 | 필터 체인 맨 앞에서 거름 |
| 정확도 40m 초과 | 무조건 버림 |
| 거리 게이트 = `3.0m + min(정확도, 15m) × 0.15` → 최대 **5.25m** | `worstAccuracyM`은 물리량이 아니라 벤더 추정치. 캡이 없으면 정확도 20m 기기는 6.0m, 6m 기기는 3.9m로 갈림 |
| 순간이동 필터 35m · 최대 러닝 속도 8.5m/s | 사람이 낼 수 없는 구간 제거 |
| 신호 끊김 30초 초과 구간 | 0m 처리하고 앵커만 이동(`af34db32` — 고가 구간에서 GPS가 죽은 사이의 직선이 통째로 적립돼 **+0.8km** 부풀던 문제. 나이키런 3.0km 대 우리 3.8km) |

**애매한 경우** — 정지 억제 반경은 캡에서 **예외**입니다. 이미 정지로 분류된 세그먼트만 버리므로 커져도 진짜 러닝을 삼킬 수 없고, 좁히면 신호등에 서 있는 동안 멀티패스 드리프트가 거리로 들어옵니다.

### 화면꺼짐 갭 정산

| 경계값 | 처리·이유 |
| --- | --- |
| 크레딧 = 포획한 네이티브 − **정산 시점**의 JS | 포획 시점의 JS가 아님. JS가 스스로 되찾은 만큼은 자동으로 빠짐 |
| 포획 문턱 **45초**(= 신호 끊김 30초 + 15초) | 더 짧은 공백은 라이브 필터가 이미 적립하므로 크레딧을 주면 이중 |
| 크레딧 바닥 **80m** | 그 미만은 갭이 아니라 두 누적기의 필터 차이. 콜드스타트 직후 화면을 끄면 네이티브가 워밍업 지터를 수십 m 더 셈 |
| 상한 = 잠든 시간 × 최대 주행 속도 | 잠든 사이 생긴 값이 물리적으로 가능한 범위를 넘지 못하게 |

### 부정행위 판정

| 경계값 | 처리·이유 |
| --- | --- |
| 0.5km 미만 / 2.4m/s 미만(≈6:57/km) | **판정 안 함** — 콜드스타트 잡음, 걷기와 구분 불가 |
| 평균 5.6m/s 초과 **그리고** 1.5km 이상 | 차량으로 판정(2:59/km를 1.5km 유지 = 세계기록급) |
| 평균 7.0m/s 초과(거리 무관) | 차량으로 판정(2:23/km, 500m도 스프린트 세계기록권) |
| 평균 케이던스 90spm 미만 | `suspect` — **텔레메트리 전용**, 처벌 없음 |
| 워치독 창 90초 안에서 **20spm 미만** | 스트라이크 1. 깨끗한 창은 하나 되돌림, **2회면 실격** |
| 보폭 **2.2m 초과**(최소 이동 90초) | 경고 + **집계 제외**, 실격 아님 |
| 서버 최종 확인(앱 판정이 놓친 경우의 마지막 관문): 포그라운드 180초 + 앱 경고 1회 이상 + 20spm 미만 | **차량으로 판정**. 앱이 한 번도 경고하지 않은 러너를 서버가 조용히 실격시키지는 않음 |
| 복귀 유예 15초 / 틱 간격 5초 초과 | 증거에서 배제(센서 재등록, JS 수면 틈) |

**애매한 경우를 두 갈래로 나눴습니다.** 근제로(20spm 미만)는 거치된 폰의 차량 서명이므로 **실격**(포인트 0)입니다. 보폭 초과는 걸음은 찍히는데 그 걸음으로 갈 수 없는 거리이지만, 걸음을 절반 이하로 세는 폰(유모차·거치대)도 넘을 수 있어 **집계 제외만** 합니다. 사람의 달리기 보폭은 0.8~1.8m이고 최상급도 1.85m라 2.2m는 여유선입니다.

**파급 범위** — 차량 판정은 **그 사용자가 얻은 LP만** 소급 회수합니다. 진 매치의 LP 손실은 환불하지 않고, 상대의 LP와 매치 판정은 건드리지 않으며, 개인 기록 화면에는 그대로 남습니다. 사라지는 것은 순위·포인트·별뿐입니다.

## 6. 설계 결정과 대안

**결정 1 — 두 원장을 더하지 않고 `max`로 병합.** 합으로 하면 이중 적립을 막기 위해 "OS가 밀린 픽스를 재생했는가"를 판별해야 합니다. `max`는 그 판별을 없앱니다. 갭 정산도 같은 원리라, JS가 스스로 되찾은 만큼은 빼는 쪽이 자동으로 차감합니다. **버린 대안**은 재생 감지 + 조건부 크레딧이었고, 그걸 버리면서 판별 블록 전체·상태 하나·상수 하나·인자 둘, 그리고 서로 반대 방향의 오적립 두 종류가 함께 사라졌습니다.

**결정 2 — 보정계수 대신 입력 자체를 통일.** 안드로이드를 iOS 쪽으로 **올려서** 맞췄습니다. **버린 대안**은 플랫폼별 거리 보정계수였고, 버린 이유는 2절에 적었습니다.

**결정 3 — 봉인을 '잠정'으로.** 되돌릴 수 없는 것(LP, 결과 알림, 저장된 기록 갱신)을 전부 창이 닫힐 때까지 미뤄, 잠정 판정에서 되돌릴 수 없는 일이 일어나지 않게 했습니다. **버린 대안**: 첫 완주 즉시 확정(이긴 사람이 지는 사고가 남음), 무한 대기(상대가 결과 화면에 갇힘).

### 되돌릴 수 있게 만든 장치 (세 결정 공통)

네이티브 거리 병합에는 킬스위치가 상수로 박혀 있어, 끄면 `max(jsKm, 0) === jsKm`이 되어 순수 JS 경로로 떨어집니다. **OTA**(스토어 심사 없이 JS 번들만 내려보내는 무선 업데이트)로 즉시 가능합니다. 네이티브 모듈 3개는 `available` 플래그와 `typeof` 가드를 통과해야 동작하고 없으면 무동작이라, 구버전 바이너리에 새 번들을 내려도 깨지지 않습니다. 판정 문턱은 전부 이름 붙은 상수 하나입니다. 보폭 판정을 실격이 아니라 집계 제외로 시작한 것도 같은 이유입니다. 억울한 사례가 나와도 되돌릴 것이 작습니다.

### 센서가 바뀌어도 남는 것

이 앱의 입력은 GPS와 걸음 센서지만, 여기서 고른 구조 셋은 센서 종류에 기대지 않습니다.

1. **판정을 확신도에 따라 두 갈래로 나눈 것** — 서명이 분명하면 처벌, 애매하면 집계 제외. 잡음 섞인 센서로 사람의 움직임을 판정할 때 한 갈래만 두면 문턱이 늘 너무 높거나 너무 낮습니다.
2. **문턱을 전부 이름 붙은 상수 하나로 두고 킬스위치를 남긴 것** — 현장 데이터가 문턱을 부정할 때 코드 구조가 아니라 값 하나만 움직이면 됩니다.
3. **억울한 판정 0건을 적발률 위에 둔 것** — 순서를 먼저 정해 두면 경계 사례에서 매번 다시 싸우지 않아도 됩니다.

## 7. AI 코딩 툴 사용 방식

이 앱은 AI 코딩 툴(주로 Claude Code)과 함께 혼자 만들었습니다. `de0b41c0` 기준 병합 제외 커밋 1,295개 중 651개에 `Co-Authored-By: Claude` 표기가 있고, 2026년 6월 이후로는 753개 중 646개(**86%**)입니다. 세는 명령은 `git log --no-merges --since="2026-06-01T00:00:00+09:00" --grep="Co-Authored-By: Claude"`입니다(`--since=2026-06-01`처럼 시각을 빼면 git이 실행 시각을 붙여 6월 1일 커밋이 잘립니다 — 앞선 표기가 737이었던 이유입니다).

**제가 정한 것**: 무엇이 공정한 판정인가(실격을 근제로 대역으로 좁힌 것, 보폭 판정을 집계 제외로 둔 것, 부정 판정이 상대 LP를 건드리지 않게 한 것), 우선순위, 배포 시점, 그리고 실기기 측정. **AI에게 맡긴 것**: 구현, 원인 추적의 1차 분석, 테스트 작성, 관점별 적대 검증.

**검증한 방법은 셋입니다.**

1. **병렬 에이전트 적대 검증.** 여러 에이전트를 '이중 적립', '기록 손실', '래치', '회귀' 같은 관점별로 띄워 반박하게 하고, 재현되거나 코드로 추적된 지적만 반영합니다. 적대 검증을 적은 커밋이 **97개**입니다(`git log --no-merges -i -E --grep="적대|반박|회의적|adversarial"`, 첫 기록 2026-06-15). 화면꺼짐 수술 때는 30개 에이전트가 19건을 확정했고, 그중 하나는 쓰던 라이브러리에 필요한 값(`nativeBuildVersion`)이 아예 없어 **기능 전체가 조용히 꺼져 있던** 문제였습니다. 단위 테스트로는 잡을 수 없는 종류입니다. 이 검증이 1차 설계를 버리고 결정 1로 가게 했습니다.
2. **변이 검증.** 신선도 수정에 처음 붙인 회귀 테스트 3개가 **수정을 되돌려도 통과**했습니다. 두 타임스탬프가 같은 밀리초에 찍혀, 깨진 구현에서도 등식이 성립했기 때문입니다. 시계를 고정해 다시 쓴 뒤 되돌리면 3개 중 2개가 실패하는 것까지 확인했습니다. 당시 사례연구에 적어 둔 실측 변이 생존률은 약 95%입니다([screen-off-record-loss.md](case-studies/screen-off-record-loss.md)).
3. **실기기 확증.** 두 폰을 나란히 들고 같은 코스를 뛰고, 출시 후에도 판정을 직접 우회해 봅니다(R4).

**AI가 틀렸던 자리도 남아 있습니다.** [`docs/case-studies/`](case-studies/) 4편은 모두 처음 무엇을 의심했고 그것이 왜 틀렸는지를 먼저 적습니다. 코드를 정확히 읽은 진단이 '정상 동작'으로 결론 내렸다가, 기기 관찰 한 줄에 뒤집힌 적이 있습니다. 'iOS는 OS 한계'라던 판단이 사실은 **링크조차 안 된 코드**를 근거로 서 있던 적도 있습니다.

## 8. 리스크와 남은 일

- **거리 패리티 수정 후 두 폰 A/B 미실시.** 다른 후보는 코드로 배제했고, 남은 사실을 설명하는 후보는 하나입니다. 다만 수정 후 대조 측정을 아직 못 해서 확증은 아닙니다. 곡률 표도 하한이고, 4m 사전 게이트의 기여분은 계량하지 않았습니다.
- **잠든 '동안'의 상대 화면.** 깨어나는 순간의 스냅백은 정확해졌지만, 잠든 중 실시간 병합은 이후 네이티브 빌드에서 따로 들어갔습니다.
- **리플레이 안티치트와 매치 전체 되돌리기**는 백로그입니다. `suspect` 대역(90spm 미만)은 일부러 텔레메트리만 켜 뒀고, 배포 후 데이터로 대역이 깨끗한 것이 확인돼야 처벌 문턱을 올립니다.
- **Postgres 전환 잔여.** 관계형 `runs` 테이블 경로가 아직 연결되지 않았고, 연결할 때 `integrity` jsonb 컬럼을 끝까지 배선하지 않으면 차량 플래그가 왕복에서 유실됩니다(코드 주석에 경고로 남겼습니다).
- **수용한 잔여(문서화됨).** 크레딧이 목표 거리를 넘기는 완주는 설계상 합법입니다. 그게 원래 받았어야 할 완주입니다.
- **실사용자 규모**는 이 문서 기준일에 세지 않았습니다. 추정치는 쓰지 않습니다.
