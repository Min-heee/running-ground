## Data contract
PER-PARTICIPANT CHECKPOINT ARRAY (compact, bounded, jsonb-hot-store-safe):
- Add one field `checkpoints: []` to buildSessionParticipant (matchSessionLifecycle.mjs:111-125). It is a COMPACT parallel number[] — checkpoints[k] = distanceKm (2 dp) at grid time T=(k+1)*10s, k=floor(elapsedSeconds/10). Index encodes T, so NO per-entry timestamp is stored. This is the smallest serialized footprint (short numbers, no keys) and is critical because store.mjs:207-211 re-serializes the WHOLE store as one JSON blob on every 2.5s mutation. An array-of-objects would inflate every push and defeat the no-change-skip (store.mjs:484).
- BOUND: MATCH_CHECKPOINT_STEP_SECONDS=10 and MATCH_CHECKPOINT_MAX (~120 = 20 min) in matchConstants.mjs near :75. Live compare only needs the tail (latest common index), so a hard cap is safe.
- SAMPLING: on each accepted push, right after live fields are stamped (matchActionHandlers.mjs:474-483), inside the !skipFinishedRepushLiveStamps block AND only when effectiveStatus ∈ {running,background} (parity with contributesToLiveCheckpoint gate matchSessionSnapshots.mjs:182): k=floor(normalizedProgress.elapsedSeconds/10); BACKFILL checkpoints[lastIdx+1..k]=lastKnownDistance (a push at elapsed=27 then 52 must fill k=2..5, else commonMaxIndex stalls on a screen-off gap); checkpoints[k]=normalizedProgress.distanceKm (last-write-wins within the 10s window; monotonic since normalizeRunningMatchProgress already makes distance monotonic). Do NOT sample on finished/forfeited/paused pushes, and key off the elapsed of the sample that CARRIED a distance, not a time-only backfill (resolveServerBackedElapsedSeconds advances elapsed without a distance).

LATEST COMMON CHECKPOINT (served comparison object):
- New pure helper resolveCommonCheckpoint(participants): restrict to running/hasProgress runners (same set as liveCheckpointSnapshots matchSessionSnapshots.mjs:222); commonMaxIndex = MIN over that set of each runner's highest-filled index; commonT=(commonMaxIndex+1)*10; per runner comparedDistance = checkpoints[commonMaxIndex]. EXCLUDE finished/forfeited/disconnected runners from the min so one stale runner cannot pin everyone low.
- SERVE additively: in buildOfficialSessionStandings (matchSessionSnapshots.mjs:221-245) OVERWRITE officialElapsedSeconds=commonT and officialDistanceKm=checkpoints[commonMaxIndex] IN PLACE OF projectOfficialDistanceKm (matchPureHelpers.mjs:172-179). The existing per-runner official* fields (officialRank, officialGapAheadKm, officialGapLeaderKm, officialElapsedSeconds surfaced via buildOfficialStandingFields matchPureHelpers.mjs:182-201, and officialComparison matchPureHelpers.mjs:204-227) then become checkpoint-fair with ZERO response-shape change and ZERO client change to the gap/rank bindings. FALLBACK: when checkpoints is undefined/empty (legacy in-flight sessions, or before the first 10s elapses), fall back to the existing projectOfficialDistanceKm path so mid-run deploys never blank the live compare. Optionally add checkpointSeconds to officialComparison for the footer label the client already prints (checkpointSeconds already exists on the client DuelComparisonSnapshot, types/matchProgress.ts:75-80).

## Edge cases (test coverage)
- Opponent has no checkpoint yet at match start (commonMaxIndex<0 or opponent.checkpoints empty): the served officialDistanceKm must NOT be 0. Fall back to the projectOfficialDistanceKm path or leave officialReady false so the client shows '동기화 중' (the footer already has a sync/live-receive branch, liveMatchArenaViewModel.ts:130-132). Test: fresh match, one push each → no fake 0.00 gap.
- A checkpoint's data never arrives (a 10s bucket skipped by a screen-off/background gap): backfill checkpoints[lastIdx+1..k]=lastKnownDistance so commonMaxIndex advances and the live compare does not freeze. Test: pushes at elapsed=27 then 52 fill k=2..5.
- Runner finishes between checkpoints (e.g. finishElapsedSeconds=47, last full checkpoint k=4/T=50 not yet crossed): do NOT sample the finish push into the grid (finished is excluded from sampling); verdict uses finishElapsedSeconds independently. Test: finish at 47 → verdict unchanged, live grid not distorted by a finish snap.
- Variable-pace runner (surge then slow) where the OLD linear projectOfficialDistanceKm was wrong but the REAL 10s samples are right: assert checkpoints[k] equals the actual reported distance at that bucket, not a linear interpolation. Test: push distances 0.1@10s,0.5@20s (surge) → checkpoint[1]=0.5 not the projected ~0.2.
- Group with N runners at different checkpoints: commonMaxIndex = MIN highest-filled index over the ACTIVE running set only; a slow/paused/backgrounded runner must NOT pin everyone low, and a finished/forfeited/disconnected runner must be EXCLUDED from the min. Test: 3 runners at k=8,8,3 where the k=3 one is paused → excluded → common=8; if k=3 is still running → common=3 and all rank on index 3.
- Forfeit mid-race: forfeited runner excluded from the common-checkpoint set (same gate as finished); their row shows the server forfeit result, not a checkpoint distance. Test: forfeit at k=5 → common advances off remaining runners, verdict is the forfeit verdict.
- Legacy in-flight session created before the checkpoints field exists (mid-run deploy): checkpoints undefined on every reader → treat as 'no checkpoint yet' → fall back to projectOfficialDistanceKm so the live compare does not blank. Test: participant object without checkpoints → official path still returns a value.
- Stale-frozen common checkpoint interacting with the existing isMyMatchDistanceStale suppression (useLiveGapNotificationScheduler.ts:60-64, staleness stamp RuntimeModel.tsx:811-818): a frozen opponent common-checkpoint must not reintroduce the phantom gap the staleness gate already suppresses. Test: opponent pushes stall → gap does not tick past the staleness window.

## Riskiest part
Stage 2 — flipping buildOfficialSessionStandings (matchSessionSnapshots.mjs:221-245) from continuous projectOfficialDistanceKm to the discrete latest-common-checkpoint. It is the single point where the whole fairness behavior changes AND it sits one function away from the finisher sort that decides the verdict. The risk is twofold: (1) accidentally letting a stale/paused/finished runner pin commonMaxIndex low and freeze the entire live comparison/leaderboard (must exclude non-active runners from the min and backfill gaps); (2) any future or accidental coupling of the finisher sort to the now-checkpoint officialDistanceKm would silently move win/lose. Mitigate with (a) a test asserting the verdict is byte-identical when checkpoint distances are arbitrarily perturbed, (b) a test that the common-checkpoint min ignores finished/forfeited/paused/disconnected runners, and (c) the mandatory undefined-checkpoints → projectOfficialDistanceKm fallback so mid-run deploys and pre-first-checkpoint states never blank or zero the compare. Secondary risk lives in Stage 1's hot-path sampling defeating the store no-change-skip if the array is stored fat — enforced compact number[] mitigates it.
